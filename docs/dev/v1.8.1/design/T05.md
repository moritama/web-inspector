# T05 設計メモ — OSV の Debian / Ubuntu データの取り込み

## 目的

第3段階（T06 の CVE ごとの判定）の材料として、OSV の Debian / Ubuntu のデータから「リリース×ソースパッケージ」ごとに CVE の修正状況（修正版・区分・ESM の印・OSV ID）を取り込み、advisory-db.json の `distro.advisories` に入れる。出典 `distro._source`（OSV と endoflife.date）を必須にし（H2）、`distro` 節のサイズ上限 800 KB を check-size と build-db / validateDb で検査する（H8・§5.3）。

## 仕様の解釈

| # | 指示書 | テストで確かめる形 |

指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **「影響なし」の表し方（§5.1 で設計の工程に任された点）。** 一次資料を確かめた結果、OSV の Debian / Ubuntu データには「影響なし」を直接表す項目が無い。Ubuntu は not-affected と DNE（そのリリースに無い）を affected に**載せない**（Ubuntu の OSV の説明）。Debian の変換器は「resolved かつ fixed_version が "0"」（影響なし）のリリースを**飛ばす**（osv.dev の変換器のソース）。つまり「載っていない」は「影響なし」「そのリリースに無い」「まだ評価していない」の区別がつかない。**載っていないことから not-affected を作らない**（推定で件数から外すと H4a により要確認件数から消えるため、安全側ではない）。圧縮後の形では、その CVE をそのリリースに記録しない。T06 ではその CVE は `no-data`（第1段階のまま。要確認件数に数える）になる。区分 `not-affected` は形としては受け付ける（validateDb・型）が、v1.8.1 の build-db は作らない。
2. **CVE 単位のレコードを優先する。** OSV の問い合わせは、CVE 単位のレコード（`UBUNTU-CVE-*`・`DEBIAN-CVE-*`）と通知単位のレコード（`USN-*`・`DSA-*`・`DLA-*`・`DTSA-*`）の両方を返す。通知単位のレコードは `upstream` に複数の CVE を持ち、どの CVE がどのリリースで直ったかまでは表さない（実際の USN-6885-1 でも、`details` にある CVE が `cves_map` に無い例があった）。そこで、同じ「リリース×ソースパッケージ×CVE」に CVE 単位のレコードがあれば、区分と修正版はそれだけで決める。無いときだけ通知単位のレコードを使う。OSV ID はどちらのものも残す（§5.2「元の OSV ID を残す」）。
3. **修正版が複数あるとき。** 同じ CVE に別々の修正版が出ることがある（勧告と再修正など）。パイプライン（.mjs）からは T01 の dpkg 比較（src の TypeScript）を使えず、別の比較を書くと二重になるので、**並べ替えずに全部残す**（`fixedVersions` は重複を除いた配列。順序は文字列の昇順で、決定的にするためだけのもの）。T06 では「パッケージ版がすべての修正版以上なら fixed」とするのが安全側（T06 の設計で決める）。
4. **ESM の印。** `esm: true` は「標準のエコシステム（`Ubuntu:20.04:LTS`）には修正が無く、Ubuntu Pro のエコシステム（`Ubuntu:Pro:20.04:LTS`）か `+esm` / `~esm` の付いた版にだけ修正がある」ときだけ付ける。標準の修正があれば標準の版を採り、`esm` は付けない（false は書かない。サイズを減らすため）。
5. **使えない値。** 取り下げられたレコード（`withdrawn` あり）は使わない。版として読めない修正版（例 `<not-affected>`。Debian の変換器は fixed_version を加工せずに出すので、ありうる）は修正の根拠にしない。CVE ID が取れないレコードは使わない。どれも build-report に数える。
6. **「データ無し」と「0 件」を区別する。** 取得結果（スナップショット）が無い対象は、`advisories` にキーを作らず警告する（T06 で no-data）。取得できて 0 件なら空の配列。Ubuntu の LTS は標準と Pro の 2 つのエコシステムを使うので、**どちらか一方でも取得結果が無ければ、その対象は出さない**（片方だけで判定すると ESM の修正を見落とすか、標準の修正を見落とす）。
7. **出典の定義の置き場所。** `_source` の `name`・`url`・`ecosystem`・`license`・`licenseNote` は人が管理する値（v1.8.2 のライセンス対応で人が直す）なので、catalog.json の `distroSources` に置く（T05 で catalog.json は変更してよい）。`retrievedAt` と `recordCount` は build-db が取得結果から入れる。`distro` 節を作るときに定義が無い・欠けている・license も licenseNote も無いなら build-db は失敗する（人が編集する値の誤りなので黙って捨てない）。
8. **`build-db --check` が `_source` の欠落で失敗すること。** `--check` は生成した DB とコミット済みの DB を比べるだけなので、`_source` が無ければ比較でも落ちる。ただ、何が悪いのか分かるよう、`--check` は**比べる前に**コミット済みの DB の `distro` 節を検査し（`validateDistroSection`）、`_source` の問題ならそのことを出力する。生成の側（`buildDatabase`）も、作った `distro` 節を同じ関数で検査する。
9. **endoflife.date のライセンス。** endoflife.date のリポジトリの LICENSE は MIT（著作権表示＋MIT の許諾文）。データ単独のライセンスの表示は見つからなかったが、§5.2 が「endoflife.date、MIT」と指定しているので `license: 'MIT'` にする。Debian（Debian Security Tracker から OSV が変換したもの）は一次資料でライセンスを確認できなかったので、§5.2 のとおり `license: null`・`licenseNote: 'v1.8.2 で確認'`。
10. **Ubuntu の LTS の判定。** エコシステム名に `:LTS` を付けるかどうかは、リリースの番号が「偶数年の .04」かで決める（Ubuntu の LTS は偶数年の 4 月）。H8 のリリース（18.04・20.04・22.04・24.04・26.04 が LTS、26.10 が中間）はこれで正しく分かれる。Ubuntu Pro（`Ubuntu:Pro:`）は LTS だけに問い合わせる。
11. **`distroMap` を渡さない呼び出し。** T02 のテストは `fetchUpstream` に `distroMap` を渡さない。渡されないときは OSV のディストリのデータを取らない（T02 の挙動のまま）。CLI（`main()`）は `PATHS.distroMap` を読んで渡す。
12. **サイズの数え方。** `Buffer.byteLength(JSON.stringify(db.distro))`（空白なし）。総合チェック C17 と同じ。KB は 1024 バイト（既存の 2 MB・3 MB と同じ）。上限を超えたら古いリリースから外さず失敗させる（§5.3）。実データで 800 KB に近づく可能性がある（Debian の CVE 単位のレコードは、そのリリースより前に直った古い CVE も含む）。超えたら人が対象を決める。

**保存するファイル**: `<upstreamDir>/osv-distro/<safeFileKey(ecosystem)>__<safeFileKey(name)>.json` に `{ package: { ecosystem, name }, fetchedAt, vulns: compact[] }`（`vulns` は `id` の昇順）。

**`buildDistroAdvisories` の規則**（対象ごと。`targets` の順）:

1. 対象の `ecosystems` のどれか 1 つでも `osvDistro[`${eco}:${sourcePackage}`]` が無ければ、その対象は出さず、警告「OSV のディストリのデータがありません: <release> <sourcePackage>（<eco>）」（release と sourcePackage を必ず含める）。
2. 全エコシステムのスナップショットの `vulns` から、`withdrawn` のあるものを除く（skipped `withdrawn`）。同じ `id` が複数のエコシステムで返ったら 1 つにまとめる。
3. 各レコードの、対象のエコシステムの `affected` の各行を「観察」にする: `{ osvId, cveLevel, fixed: string|null, esm }`。
   - `fixed` の値は `/^[0-9][0-9A-Za-z.+~:-]{0,99}$/` に合うものだけ使う。合わない値しか無ければその行は捨てる（skipped `invalid-fixed`）。合う値が複数あれば、それぞれ 1 つの観察にする。
   - fixed が無く introduced だけなら `fixed: null`（未修正）。
   - `esm` は「エコシステム名に `:Pro:` を含む」または「fixed が `/[+~]esm\d*/` を含む」。
   - 観察を、レコードの各 CVE（`cves`）に割り当てる。`cves` が空のレコードは捨てる（skipped `no-cve`）。
4. CVE ごとに: CVE 単位の観察（`cveLevel: true`）が 1 つでもあれば、区分と修正版はそれだけで決める。無ければ通知単位の観察で決める。
   - 標準（`esm: false`）の修正がある → `{ status: 'fixed', fixedVersions: <標準の修正版> }`
   - 標準の修正が無く ESM の修正がある → `{ status: 'fixed', fixedVersions: <ESM の修正版>, esm: true }`
   - どちらも無い → `{ status: 'open', fixedVersions: [] }`
   - `osvIds` は、その CVE に割り当てた全観察（CVE 単位・通知単位の両方）の OSV ID。重複を除き昇順。
5. 出力の 1 件は、キーをこの順で `{ cve, status, fixedVersions, esm?, osvIds }`。`esm` は true のときだけ書く。`fixedVersions` は重複を除き昇順。CVE は `cve` の昇順。
6. `advisories[release][sourcePackage] = entries`（取得できて 0 件なら `[]`）。キーの順は targets の順（決定的であればよい）。
7. 「影響なし」を推定しない: affected に対象のエコシステムの行が無い CVE は記録しない（解釈 1）。`not-affected` を作らない。

**`buildDistroSources` の規則**:

- `definitions`（catalog の `distroSources`）が配列でない、`ecosystem: 'Debian'`・`ecosystem: 'Ubuntu'`・`ecosystem: null かつ url が https://endoflife.date/ で始まる` の 3 つのどれかが無い → Error（メッセージに `distroSources` と、欠けたもの（`Debian` / `Ubuntu` / `endoflife.date`）を含める）。
- 各定義: `name` が空でない文字列、`url` が https の URL、`license` が空でない文字列か、`license` が null で `licenseNote` が空でない文字列。どちらでもない → Error（メッセージに `license` と `licenseNote` を含める）。
- 出力（定義の順）: `{ name, url, ecosystem, license, ...(licenseNote ? { licenseNote } : {}), retrievedAt, recordCount }`
  - OSV（Debian / Ubuntu）: `retrievedAt` は、その系統の対象で使ったスナップショットの `fetchedAt` のうち最も新しいもの（無ければ null）。`recordCount` は、その系統の `advisories` の全 CVE の `osvIds` の種類数（無ければ 0）。
  - endoflife.date: `retrievedAt` は `distroEol` のスナップショットの `fetchedAt` のうち最も新しいもの（無ければ null）。`recordCount` は `distro.releases.length`。

### 3. `scripts/advisories/lib/distro.mjs`

- `export const DISTRO_SECTION_MAX_BYTES = 800 * 1024;`
- `validateDistroSection(distro)` に足す（既存の検査はそのまま）:
  - `distro.advisories` か `distro._source` のどちらかがあれば、**両方**が必要（無ければ Error。`_source` が無いときのメッセージは `distro._source` を含める）。どちらも無ければ（T02 までの DB・固定 DB）これまでどおり通す。
  - `_source`: 空でない配列。`ecosystem === 'Debian'`、`ecosystem === 'Ubuntu'`、url が `https://endoflife.date/` で始まる要素が各 1 つ以上（無ければ Error。メッセージに `_source` と欠けたもの）。各要素: `name` が空でない文字列、`url` が https、`license` が空でない文字列か `licenseNote` が空でない文字列（どちらも無ければ Error。メッセージに `license`）、`retrievedAt` が null か ISO 日時の文字列、`recordCount` が 0 以上の整数。
  - `advisories`: オブジェクト（配列でない）。キーは `/^(debian|ubuntu):[0-9][0-9.]*$/`。値はオブジェクトで、キーは `/^[a-z0-9][a-z0-9.+-]+$/`、値は配列。各要素:
    - キーは `cve`・`status`・`fixedVersions`・`esm`・`osvIds` だけ
    - `cve`: `/^CVE-\d{4}-\d{4,7}$/`
    - `status`: `'fixed'`・`'open'`・`'not-affected'` のどれか
    - `fixedVersions`: 配列で各要素が `/^[0-9][0-9A-Za-z.+~:-]{0,99}$/`。`status === 'fixed'` なら 1 つ以上、それ以外は空
    - `esm`: 無いか `true`（`true` は `status === 'fixed'` のときだけ）
    - `osvIds`: 1 つ以上で、各要素が `/^(?:USN|LSN|UBUNTU|DEBIAN|DSA|DLA|DTSA)-[0-9A-Za-z.-]{1,60}$/`
  - サイズ: `Buffer.byteLength(JSON.stringify(distro)) > DISTRO_SECTION_MAX_BYTES` なら Error（メッセージに `distro` と `800` を含める）。
- `buildDistroSection({ distros, distroEol, distroMap })` はそのまま（T02）。advisories と _source は build-db が足す。

### 4. `scripts/advisories/build-db.mjs`

- `loadUpstream(dir)` の戻り値に `osvDistro: {}` を足し、`<dir>/osv-distro/*.json` を名前順に読んで `osvDistro[`${json.package.ecosystem}:${json.package.name}`] = json`。
- `buildDatabase(...)`（引数はそのまま）: `distro` 節を作るとき（`catalog.distros` か `distroMap` があるとき。T02 と同じ条件）に、
  1. `targets = osvDistroTargets(distroMap)`（distroMap が無ければ []）
  2. `{ advisories, warnings } = buildDistroAdvisories({ targets, osvDistro: upstream.osvDistro || {} })`
  3. `_source = buildDistroSources({ definitions: catalog.distroSources, osvDistro: upstream.osvDistro || {}, distroEol: upstream.distroEol || {}, advisories, releases: distro.releases })`
  4. `distro` のキーの順は `releases, map, advisories, _source`。
  5. `validateDistroSection(distro)` を呼ぶ（800 KB を超えたらここで例外）。
  6. `report.distro` に `advisories: <対象の数>`, `advisoryEntries: <CVE の件数>`, `skipped` を足し、`warnings` に OSV の警告を足す。
  7. `sources` 配列の `'OSV.dev (GitHub Advisory Database / npm / Packagist)'` の後に `'OSV.dev (Debian Security Tracker / Ubuntu Security Notices)'` を足す（`distro` 節を作るときだけ。それ以外の DB の `sources` は変えない）。
  - `libraries`・`coverage`・`integrity.digest` の計算は変えない。`integrity.distroDigest` は `distro` 節全体（advisories と _source を含む）の sha256。
- `main()` の `--check`: 生成の前に、コミット済みの DB があり `distro` 節を持てば `validateDistroSection(committed.distro)` を呼び、失敗したら `[build-db] --check 失敗: <メッセージ>` を出して終了コード 1。そのあと従来どおり生成して比べる。生成で例外が出たら（出典の定義の誤り・800 KB 超え）、既存の catch が終了コード 1 にする（メッセージは標準エラーに出る）。

### 5. `scripts/advisories/fetch-upstream.mjs`

- `fetchUpstream({ …, distroMap })` に引数 `distroMap`（省略可）を足す。
- `fetchOsvDistro()`: `osvDistroTargets(distroMap)` の各対象の各エコシステムについて、`record('osv-distro:<ecosystem>:<sourcePackage>', <ファイル>, …)` で取得・圧縮・保存（`fetchOsvDistroPackage` → `compactOsvDistroVuln`、`id` 昇順）。`count` はレコード数。同じエコシステム×パッケージは 1 回だけ。distroMap が無ければ何もしない。
- `args.distroOnly` のとき: OS のライフサイクル（T02）に続けて `fetchOsvDistro()`。それ以外の挙動（manifest の `fetchedAt` を前回のまま、前回の sources を引き継ぐ、製品・KEV・NVD・PSL を取らない）は T02 のまま。
- 通常の取得（`args.only` なし）: OS のライフサイクルに続けて `fetchOsvDistro()`。`args.only` があるときは取らない。
- OSV のディストリのレコードの CVE は NVD のスコア補完の対象（`cveIdsNeedingScore`）に入れない（ディストリのデータにスコアは使わない）。
- `main()`: `readJson(PATHS.distroMap, null)` を `distroMap` として渡す。`minIntervalMs` は既存の `api.osv.dev: 100` のまま。

### 6. `scripts/validate-advisories.mjs`

`validateDistroSection` を呼んでいる（T02）ので、lib/distro.mjs の追加だけで `_source`・`advisories`・サイズが検査される。変更は不要のはず（必要なら直してよい）。

### 7. `scripts/ci/check-size.mjs`

- `SIZE_LIMITS` に `distro: 800 * 1024` を足す（`advisoryDb`・`dist` はそのまま）。
- `checkSizes()`: DB のファイルがあり、JSON として読めて `distro` を持つときだけ、`{ target: 'distro', path: advisoryDbPath, bytes: Buffer.byteLength(JSON.stringify(db.distro)), limit: SIZE_LIMITS.distro, level: classifySize(bytes, limit) }` を `results` に足す。JSON として読めない・`distro` が無いときは足さない（既存のテストは JSON でない合成ファイルを使う）。`ok` は従来どおり「fail が 1 つも無い」。
- `main()` の出力は既存の形（`[${res.target}]` を含む `::error` / `::warning`）のままでよい（`[distro]` が行に入る）。

## 実装の担当への注意

- **ネットワークに出ない。** OSV の実際の取得はスクリプトが T05 の後に行う（H10）。`data/advisories/upstream/` に何も置かない。取得前の同梱 DB は `distro.advisories` が `{}` で正しい。
- **`advisory-db.json` と `build-report.json` を手で作らない・直さない。** invariants の T05 の追記は、実装の後の build-db で通る。
- **「影響なし」を推定しない（H4）。** affected に無いことから `not-affected` を作らない。「安全」「該当なし」の語を書かない（C18）。
- **既存の出力を変えない。** `libraries`・`coverage`・`integrity.digest`、distro 節の無い DB の `sources`、T02 の `releases`・`map` の形はそのまま。OSV のディストリのデータを `libraries` に混ぜない（C13）。
- **`fetchUpstream` に `distroMap` が渡されないときは OSV のディストリのデータを取らない**（T02 のテストがこの呼び方をする）。`--distro-only` で manifest の `fetchedAt` を進めない（T02 のまま）。
- **Ubuntu の LTS は標準と Pro の 2 つのエコシステム**。どちらかの取得結果が無い対象は出さない（解釈 6）。中間リリースに Pro は無い。
- **版の比較をしない。** パイプラインでは修正版の大小を比べない（T01 の比較は src の TypeScript）。`fixedVersions` は重複を除いて文字列の昇順に並べるだけ。
- check-size は、JSON として読めない DB（既存のテストの合成ファイル）で失敗しないこと。
- `--check` は、比べる前にコミット済みの DB の distro 節を `validateDistroSection` で検査し、出力に原因（`_source` など）を出すこと（テストが出力の `_source` を見る）。
- 出典の定義のエラーメッセージに `license` / `distroSources` / 欠けたもの（`Debian`・`Ubuntu`・`endoflife.date`）を、サイズのエラーに `distro` を含めること（テストが正規表現で見る）。
- 表に無い値（エコシステム名、ライセンス、出典の URL）を足さない（K6）。
