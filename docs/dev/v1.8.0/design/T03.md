# T03 HSTS の 1 行化とプレリリース表記 — 設計メモ

## 目的

HSTS に preload があり max-age が 1 年未満のとき、SEC-HSTS-02 と SEC-HSTS-03 の 2 行が出る重複をなくし、SEC-HSTS-02 の 1 行にまとめる。あわせて、version-matcher が SemVer 2.0 の書式のプレリリース識別子を固定の語に限らず受け付け、ビルドメタデータを比較で無視するようにする。

## 仕様の解釈

### HSTS

| # | 指示書 | 解釈（テストで確かめること） |
| --- | --- | --- |
| H1 | preload があり max-age が 1 年未満なら SEC-HSTS-02 の 1 行だけにする | `0 < max-age < 31536000` かつ preload のとき、`checkHttpHeaders` の結果のうち `SEC-HSTS-` で始まるものは SEC-HSTS-02 の 1 件だけ。SEC-HSTS-03 は出ない |
| H2 | 説明に「preload の登録条件も満たしていない」を付け加える | H1 の場合、SEC-HSTS-02 の `description` に文字列 `preload の登録条件も満たしていない` が含まれる（指示書が文言を指定しているので、この文字列だけを確かめる。前後の文や句読点は問わない）。preload が無いときの SEC-HSTS-02 の説明には `preload の登録条件` を含めない（陰性） |
| H3 | 重大度は max-age の区分のまま | 同じ max-age で preload の有無を変えても、SEC-HSTS-02 の `status`・`severity` は同じ（86400 未満は medium、86400 以上 1 年未満は low） |
| H4 | SEC-HSTS-03 は max-age が 1 年以上で includeSubDomains だけが無いときに限る | 陽性: `max-age >= 31536000` かつ preload あり、includeSubDomains なし → SEC-HSTS-00（pass）と SEC-HSTS-03（info / info）。陰性: includeSubDomains もある、preload が無い、max-age が 1 年未満、max-age が 0 または未指定、のどれでも SEC-HSTS-03 は出ない |
| H5 | 受け入れ条件「`max-age=2592000; preload` のような値で HSTS の行が 1 行だけ出る。reports:lint が通る」 | `executeInspection` で作ったレポートで、`SEC-HSTS-` の指摘が 1 件、`generateMarkdownReport` の表で `| HSTS (Strict-Transport-Security) |` で始まる行が 1 行、`lintReportPair(report, md, { includePending: true })` が `ok: true`・違反 0 件 |

解釈で決めたこと:

- **max-age が 0 または未指定で preload がある場合**: max-age=0 や未指定も「1 年以上」ではないので、H4 により SEC-HSTS-03 は出さず、SEC-HSTS-02（medium）の 1 行だけにする（テストあり）。この場合の説明に H2 の文言を付けるかどうかは、指示書の「この場合」（max-age が 1 年未満）に含まれると読めるが、HSTS 自体が無効・不正という主旨が先に立つので、**付けても付けなくてもよい**（テストでは求めない）。推奨は、付ける（実装が単純で、内容も正しい）。
- **preload の判定と includeSubDomains の判定**は既存のまま（ディレクティブ名の大文字・小文字を区別しない、順序を問わない）。
- **SEC-HSTS-03 の文面**は、H4 の場合は includeSubDomains だけが足りないので、「max-age が 1 年未満」の注記は付かなくなる。テストは `description` に `includeSubDomains` が含まれることだけを確かめる。
- HTTP（非 HTTPS）のときは HSTS を評価しない既存の挙動は変えない。

### version-matcher

| # | 指示書 | 解釈（テストで確かめること） |
| --- | --- | --- |
| V1 | プレリリース識別子を SemVer 2.0 の書式全般で受け付ける | `parseVersion` が、SemVer 2.0.0 §9 の書式（`-` の後に `.` 区切りの識別子。各識別子は `[0-9A-Za-z-]` の 1 文字以上）のプレリリースを解析し、`pre` を null 以外にする。例: §9 の例 `1.0.0-0.3.7`・`1.0.0-x.7.z.92`・`1.0.0-x-y-z.--`、固定の語に無い `2.1.0-SNAPSHOT`・`5.0.0-M1`・`3.0.0-1` |
| V2 | SemVer 仕様の例の順序が成り立つ | §11 の例 `1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0` の**すべての組**で `compareVersions` が -1 / 0 / 1 を正しく返す。§11 の識別子の規則（数字だけの識別子は数値比較、数字だけの識別子は英数字の識別子より小さい、前が等しければ識別子が多いほうが大きい）を、固定の語に無い識別子でも確かめる |
| V3 | ビルドメタデータ（`+sha-…`）は比較で無視する | §10 の例と `+sha-abc1234` の形で、ビルドメタデータだけが違う版の `compareVersions` が 0。範囲の照合（`satisfiesVersionRange`）でも無視する |
| V4 | `rc1` や `-next.0` など今受け付けている表記はそのまま | `3.5.0-rc1`・`22.0.0-next.0`・`20.0.0-next.0.0.0`・`22.0.0-rc.4` が解析でき、`rc2 < rc10`（語に付いた数字の数値比較）などの既存の順序が変わらない |
| V5 | 解析できない文字列は従来どおり Unknown Version（SPEC-06） | §9 の書式に合わない（空の識別子 `1.0.0-`・`1.0.0-alpha..1`・`1.0.0-.alpha`・`1.0.0-alpha.`、使えない文字 `_`・空白・非 ASCII・`!`、空のビルドメタデータ `1.0.0+`、`+` が 2 つ）文字列は `parseVersion` が null、`satisfiesVersionRange` が false。`matchOfflineAdvisories` は `Unknown Version`。一方、§9 の書式に合う版は `Unknown Version` にならない |
| V6 | 受け入れ条件「既存の版照合テスト（version-check.test.ts など）が変更なしで通る」 | `tests/version-check.test.ts`・`tests/advisory-db-invariants.test.ts`・`tests/advisory.test.ts`・`tests/review-v1.6.5-acceptance.test.ts` を変更せずに通す |

**V1 と V6 の衝突と、その解き方（重要）**

既存のテストは、`1.0.0-nxt` を「壊れた字句」として扱うことを求めている。

- `tests/version-check.test.ts`: `satisfiesVersionRange('1.5.0', '>= 1.0.0-nxt')` と `satisfiesVersionRange('1.5.0', '>= 1.0.0-nxt, < 2.0.0')` が false
- `tests/advisory-db-invariants.test.ts`: `isValidRange('>= 1.0.0-nxt')` が false（`scripts/validate-advisories.mjs`）

しかし SemVer 2.0 の書式では `nxt` は正しい識別子なので、すべての場所で書式全般を受け付けると、上の 2 件が true になって既存のテストが落ちる。そこで、**解析する文字列の出どころで規則を分ける**。

- **観測した版**（ページから検出した版。`parseVersion`・`compareVersions`・`satisfiesVersionRange` の第 1 引数）: SemVer 2.0 の書式全般を受け付ける（V1）。`1.0.0-nxt` も観測した版としては解析でき、`1.0.0` より小さいプレリリースになる（既存のテスト `satisfiesVersionRange('1.0.0-nxt', '>= 1.0.0') === false` は、この扱いでも false のまま通る）。
- **DB の range の比較節の版**（`satisfiesVersionRange` の第 2 引数の中の版）: 従来どおりの固定の語の書式だけを受け付け、それ以外の節には一致させない。DB の range は `scripts/validate-advisories.mjs` の `isValidRange` が同じ固定の語の規則で検証しており（v1.8.0 では DB の書式を変えない）、検証が拒否する節で CVE を該当させない（壊れた DB の値では断定しない）ため。

この規則で、指示書の 3 つの受け入れ条件と既存のテストがすべて両立する。テストでは「`isValidRange` が拒否する range には、どの版も一致しない」という、検証と照合の一致を確かめる（`>= 1.0.0-nxt` のほか `< 2.0.0-x.7.z.92`・`>= 1.0.0-SNAPSHOT`・`< 2.0.0-0.3.7`）。

解釈で決めたこと:

- **大文字・小文字**: SemVer 2.0 は英数字の識別子を ASCII 順で比べる（大文字が小文字より先）が、既存の実装は識別子を小文字にしてから比べている。「今受け付けている表記はそのまま」に従い、既存の挙動を変えない（小文字にしてよい）。テストでは大文字と小文字が混ざる識別子どうしの順序を求めない。
- **数字だけの識別子の先頭の 0**（例: `1.0.0-rc.01`）: SemVer 2.0 は禁止しているが、既存の実装は受け付けて数値として比べている。今受け付けている表記を拒否すると Unknown Version が増える（断定を減らす方向ではあるが、既存の照合結果が変わる）ので、**受け付けたままにする**。テストでは求めない（受け付けても拒否しても合格）。
- **主版の部分**（`1.0`・`1.2.3.4` のような 3 要素以外、先頭の `v`、Linux ディストリビューションの印）の扱いは変えない。
- **ビルドメタデータの書式**: §10 は識別子が空でないことを求めるが、既存の実装は `[0-9A-Za-z.-]+` で検証している。空のビルドメタデータ（`1.0.0+`）と `+` が 2 つの場合だけを「解析できない」としてテストする（`1.0.0+a..b` のような空の識別子の扱いは求めない）。

## 実装の方針

### `src/security/headers.ts`（`checkHttpHeaders` の HSTS の節）

- SEC-HSTS-02 を出す 3 つの分岐（max-age が 0・未指定 / 86400 未満 / 1 年未満）で、`hasPreload` のときは `description` の末尾に、`preload の登録条件も満たしていない` を含む一文を付け加える（例: `また、preload が指定されていますが、preload の登録条件も満たしていない状態です（max-age が 1 年（31536000秒）未満）。`）。`status`・`severity`・`checkId`・`name` は変えない。max-age が 0・未指定の分岐で付けるかは任意（仕様の解釈を参照。推奨は付ける）。
- SEC-HSTS-03 の条件を `hasPreload && maxAge !== null && maxAge >= 31536000 && !hasSubDomains` に変える。文面は「includeSubDomains が未指定」だけを挙げるものにする（`max-age が 1 年未満` の注記は、この条件では出なくなる）。`observed` に `preload の登録条件を満たしていない` を含める既存の形は保つ（`tests/security.test.ts` が確かめている）。
- recommendation（SEC-HSTS-02）に preload の登録条件（max-age=31536000 以上と includeSubDomains）を足すのは任意。
- 名前は `HSTS (Strict-Transport-Security)` のまま（reports:lint の R05 が確かめる）。

### `src/security/version-matcher.ts`

- 公開 API の名前と型は変えない（`parseVersion(version): ParsedVersion | null`、`compareVersions(v1, v2): number`、`satisfiesVersionRange(version, rangeSpec): boolean`、`satisfiesSingleClause(version, clause): boolean`、`parseVersionParts`、`isLinuxPackageVersion`、`ParsedVersion`）。テストはこのうち `parseVersion`・`compareVersions`・`satisfiesVersionRange` だけを使う。
- `parseVersion(version)` の既定（引数 1 つ）を「観測した版」の規則にする:
  1. 既存の固定の語の書式（`PRERELEASE_RE`）に合えば、従来どおりに分解する（`rc1` → `['rc', 1]` のように語に付いた数字を分ける。`rc2 < rc10` を保つため）。
  2. 合わなければ、SemVer 2.0 §9 の書式（`/^[0-9A-Za-z-]+(?:\.[0-9A-Za-z-]+)*$/`）で検証し、`.` で分けた各識別子を、数字だけなら数値、それ以外は文字列（既存に合わせて小文字にしてよい）にする。
  3. どちらにも合わなければ null。
- 「DB の range の比較節の版」用に、固定の語だけを受け付ける解析を内部に持つ。名前は任意（例: 内部関数 `parseRangeTargetVersion(version)`、または `parseVersion(version, { strictPrerelease: true })` のような任意の第 2 引数）。`satisfiesSingleClause` の比較対象（`targetVer`）の解析にはこれを使う。第 1 引数（観測した版）の解析には既定の `parseVersion` を使う。
- `compareVersions` は両方の引数を「観測した版」の規則で解析する（§11 の例の順序と、固定の語に無い識別子の比較のため）。
- ビルドメタデータは今も `+` 以降を捨てているので、`+sha-…` の形はそのまま無視される。空のビルドメタデータ・`+` が 2 つは null のまま。
- コメント（`PRERELEASE_RE` と `parseVersion` の説明の「`-nxt` のような壊れた字句は拒否する」）を、新しい規則（観測した版は SemVer 2.0 の書式全般、range の比較節は固定の語）に合わせて直す。

### `docs/DETECTION_SPECIFICATION.md`

- HSTS の節（「また `preload` があるのに…`SEC-HSTS-03`」の文）を、H1〜H4 の新しい条件に合わせて直す。版の比較の記述があれば、V1・V3 と range の比較節の扱いを書く。`npm run spec:generate` で更新される部分があれば、夜間はスクリプトが実行する。

### 変更しないもの

- `scripts/validate-advisories.mjs`（`isValidRange` と `PRERELEASE_RE`）。DB の range の書式は v1.8.0 では変えない。
- `src/storage/exceptions.ts` の SEC-HSTS-03 の登録（ID は残る）。

## 実装の担当への注意

- **`1.0.0-nxt` の既存テストを壊さない**。プレリリースの書式を広げるのは観測した版の解析だけで、`satisfiesSingleClause` の比較節の版（DB の range 側）は固定の語の規則のままにする（「V1 と V6 の衝突と、その解き方」）。`scripts/validate-advisories.mjs` の `isValidRange` は変えない。
- **`rc1` の分解を保つ**。書式全般の規則だけで解析すると `rc1` は 1 つの英数字の識別子になり、`rc2 < rc10` が崩れる（ASCII 順では `rc10 < rc2`）。まず既存の `PRERELEASE_RE` を試し、合わないときだけ書式全般の規則にする。
- **Linux ディストリビューションの印**（`2.4.41-1ubuntu1` など）は、プレリリースより先に `isLinuxPackageVersion` で正式版として扱う既存の順序を保つ。書式全般の規則で `1ubuntu1` をプレリリースにしてしまうと、SPEC-02 と `tests/version-check.test.ts` の `['2.4.41-1ubuntu1', '< 2.4.41', false]` が落ちる。
- 数字だけの識別子は数値として比べる（`x.2 < x.10`）。数字だけの識別子は英数字の識別子より小さい（既存の `compareParsedVersions` の規則のままでよい）。
- HSTS の新しい文言は SEC-HSTS-02 の `description` に入れる（`observed` ではない）。レポートの表の観測値の列は従来どおりヘッダーの値。
- SEC-HSTS-02 の `name` は `HSTS (Strict-Transport-Security)` のまま（reports:lint の R05 と `src/storage/exceptions.ts` の対応表）。HSTS は既に `HEADER_DEPENDENT_CHECK_PREFIXES` に含まれるので、接頭辞の追加は不要。重大度を上げる変更はしない。
- `docs/DETECTION_SPECIFICATION.md` の HSTS の記述を新しい条件に合わせる。
- テスト（`tests/`）と設計メモは変更しない。期待値が仕様と合わないと考えたら、`.agy-out/result.json` に `needsTestChange: true` と理由を書く。
