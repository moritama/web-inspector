# T08 設計メモ — NEW-03c SRI、認証ページの Cache-Control、Cookie の有効期限と SameSite

## 目的

サードパーティの script・stylesheet に SRI（integrity 属性）が無いこと、認証系の Cookie があるページで Cache-Control に no-store が無いこと、認証系の Cookie の有効期限が長すぎることと SameSite=None を、追加の通信なしで指摘する。新しい指摘は最大 LOW（G4）。integrity の値は集めず、レポートと履歴に出さない。

## 仕様の解釈

### 各 ID の判定（解釈と理由）

- **SEC-SRI-01**（warning / low）: `dom.sriResources` のうち、次をすべて満たすもの（以下「対象」）があるとき 1 件だけ出す。
  - URL が http か https（`data:`・`blob:` は対象外）
  - `determinePartyType(url, pageUrl) === 'third-party'`（PSL による登録可能ドメインの比較。既存の `src/security/domain-analyzer.ts`）。`'local'`（IP・localhost）は対象外
  - `hasIntegrity === false`
  - 配信元が SRI-02 の一覧に**無い**
  - observed に URL を最大 10 件並べる（「最大 10 件までまとめて 1 行」）。11 件以上なら、残りの件数を「他 N 件」のように書く（推奨。テストは「12 件のうち 10 件の URL が観測値にある」ことだけ確かめる）。
  - 同じ URL は 1 回だけ数える。URL のクエリとフラグメントは除いて書く（既存の URL マスク IMPL-07 と同じ。クエリに API キーなどが入ることがあるため。テストあり）。
  - ヘッダーに依存しないので、ヘッダー未観測でも unknown にしない（接頭辞を足さない。テストあり）。
- **SEC-SRI-02**（info / info）: 上の条件のうち「配信元が一覧に**ある**」ものだけ。1 件にまとめ、書き方は SRI-01 と同じ。SRI-01 と SRI-02 の URL は重ならない。
  - 一覧（コード内の定数）は、一次資料で「配信元から直接読み込む」「自分でホストしない」または「公開のたびに内容が変わる」と確かめたものだけにする（外部の事実 1〜4）。照合はホスト名の**完全一致**と、必要なら path の前方一致。`www.googletagmanager.com.attacker.example` のような、一覧のホスト名で始まるだけの別ホストは一覧に入れない（テストあり）。

    | ホスト名 | path の前方一致 | 理由（外部の事実） |
    | --- | --- | --- |
    | `www.googletagmanager.com` | （すべて） | 1. タグマネージャー。公開のたびに配信されるコンテナが変わる |
    | `js.stripe.com` | （すべて） | 2. 決済の SDK。js.stripe.com から直接読み込み、バンドル・自前ホストをしない |
    | `www.paypal.com` | `/sdk/js` | 3. 決済の SDK。直接読み込み、互換のある変更が自動で反映される |
    | `accounts.google.com` | `/gsi/` | 4. 認証の SDK。自前ホストは非対応、更新が自動で反映される |

  - 採用しなかったもの: Apple Pay JS SDK（Apple の担当者は自動更新版での SRI を勧めないと書いているが、配信元のホスト名を一次資料で確かめられなかった）。cdn.jsdelivr.net などの公開 CDN（版を固定すれば SRI を付けられるため SRI-01 のまま。テストあり）。
- **SEC-CACHE-01**（warning / low）: `network.cookies` に認証系の Cookie が 1 つ以上あり、Cache-Control のディレクティブに `no-store` が無いとき。
  - Cache-Control が無いときも出す（no-store が無いため）。
  - 複数行は `,` でつないでから、`,` で分け、各要素の `=` より前を前後の空白を除いて小文字にして、`no-store` と完全一致で比べる。ディレクティブ名は大文字・小文字を区別しない（外部の事実 5）。`x-no-store` のような別のディレクティブは no-store とみなさない（テストあり）。
  - `no-cache` や `private` は no-store の代わりにならない（外部の事実 5。`no-cache` は保存を禁じない）。
  - 認証系の Cookie が無いページでは出さない。
  - scheme（http・https）で分けない（テストは https だけ）。
- **SEC-COOKIE-EXPIRY**（warning / low）: 認証系の Cookie のうち、`session` でなく、`expirationDate`（秒。外部の事実 6）が「調査時刻 + 365 日」を**超える**ものがあるとき 1 件だけ出す。observed に該当する Cookie 名を書く（既存と同じく最大 3 件＋「他 N 件」でよい）。
  - 「1 年」は 365 日 × 86,400 秒とする（うるう年を考えない。境界の差は 1 日で、警告を増やす向きにはならない）。ちょうど 365 日は出さない（「超える」）。
  - `expirationDate` が無い・数値でないときは出さない（断定しない）。
- **SEC-COOKIE-SAMESITE-NONE**（warning / low）: 認証系の Cookie のうち、`normalizeSameSite(sameSite) === 'none'`（Chrome API の `no_restriction`）かつ `secure === true` のものがあるとき 1 件だけ出す。observed に Cookie 名を書く。
  - Secure なしの SameSite=None は、ブラウザが保存しないので対象外（D7。v1.7.0 で関連チェックを削除した理由と同じ）。
  - Partitioned（CHIPS）の Cookie の扱いは指示書に無いので、分けない（テストしない）。

### テストでは問わないこと（実装に任せる）

- 文言の一字一句、項目名（name）、referenceUrls の中身、結果の配列の順番
- SRI-01・SRI-02 の category（推奨は下の「実装の方針」）
- 合格の項目（例: SEC-SRI-00 pass）を作るかどうか。作る場合は重大度 info にする
- integrity 属性が空文字のときの扱い（推奨は「無い」とみなす。外部の事実 7）
- noscript・template の中の script・link の扱い（推奨は集めない）
- SEC-COOKIE-00（合格）を、新しい Cookie の指摘が出たときに出すかどうか（既存どおり、指摘が 1 つでもあれば出さない形でよい）

## 実装の方針

1. **`src/shared/types.ts`**
   ```ts
   /** SRI の診断に使う script・stylesheet の情報（integrity の値は持たない）(v1.8.0 T08) */
   export interface SriResourceItem {
     kind: 'script' | 'stylesheet';
     /** 絶対 URL */
     url: string;
     /** integrity 属性があるか（値は集めない） */
     hasIntegrity: boolean;
   }
   ```
   `DomSignals` に任意のフィールド `sriResources?: SriResourceItem[]` を足す（過去の形でも壊れないように任意）。`InspectionReport` には足さない（DOM の生データはレポートに入れない）。
2. **`src/content/content-script.ts`**（`extractDomSignals`）
   - `runStep('sri', …)` で `script[src]` と `link[href]`（rel を空白で分けたトークンに `stylesheet` がある）を集める。URL は既存の `resolveToAbsoluteUrl(raw, baseUri)` で絶対 URL にする（解決できないものは入れない）。
   - `hasIntegrity` は `el.hasAttribute('integrity') && (el.getAttribute('integrity') || '').trim() !== ''` を推奨。**値を変数に保存したり、戻り値に入れたりしない**。
   - 件数の上限を設ける（推奨 200 件）。戻り値に `sriResources` を入れる。
3. **`src/security/sri.ts`**（新規）
   ```ts
   /** SRI を付けられない配信元の一覧（理由は設計メモ T08 と WORKLOG） */
   export const SRI_UNSUPPORTED_PROVIDERS: ReadonlyArray<{ hostname: string; pathPrefix?: string }>;
   export function isSriUnsupportedProvider(url: string): boolean;
   /** SEC-SRI-01 / SEC-SRI-02 を返す（どちらも 0〜1 件） */
   export function checkSubresourceIntegrity(
     pageUrl: string,
     resources: SriResourceItem[] | undefined | null
   ): SecurityCheckResult[];
   ```
   - 入力を検証する: 配列でなければ空。各要素は `url` が 2,048 文字以下の文字列、`hasIntegrity` が boolean のものだけ使う。**要素をそのまま結果に入れない**（`integrity` などの想定外のキーが混ざっても出ないように。テストあり）。
   - 別サイトの判定は `determinePartyType`、URL のクエリ・フラグメントの除去は既存の `stripUrlQueryAndFragment`（`src/shared/identity.ts`）を使う。
   - category は既存の型の値から選ぶ（推奨 `'https-communication'`。`SecurityCategory` に新しい値を足すと UI の対応表に影響するため）。推奨の name: SRI-01「サードパーティ資源の SRI (integrity) 未設定」、SRI-02「SRI を付けられない配信元の資源」。推奨文: SRI-01 は「版を固定した URL に integrity 属性（と crossorigin）を付ける」。SRI-02 は「SRI の代わりに CSP で読み込み元を限定する」。
4. **`src/security/cookies.ts`**（`checkCookies`）
   - 既存の分類（`classifyCookieAdvanced`）で `category === 'authentication'` の Cookie について、SEC-COOKIE-EXPIRY と SEC-COOKIE-SAMESITE-NONE を足す（category `'cookies'`。テストする）。新しい分類は作らない。
   - 現在時刻は `Date.now()` を使う（テストは偽のタイマーで時刻を止める）。任意の 4 番目の引数 `options?: { nowMs?: number }` を足してもよい（テストは使わない）。
   - 推奨の name: 「認証系 Cookie の有効期限が長い」「認証系 Cookie の SameSite=None」。推奨文: 有効期限は「セッション Cookie か、短い有効期限（例: 数時間〜数日）にする」。SameSite は「クロスサイトで送る必要がなければ Lax か Strict にする」。
5. **SEC-CACHE-01 の評価**（ヘッダーと Cookie の両方を見る）
   - 推奨: `src/security/headers.ts` に `export function checkAuthPageCacheControl(headers: Record<string, string[]>, cookies: Array<{ name: string }>, url: string): SecurityCheckResult[]` を作り、`src/security/engine.ts` の `SecurityEngine.evaluate` から呼ぶ。テストは関数名に依存せず、`SecurityEngine.evaluate` と `executeInspection` の結果で確かめる。
   - category `'http-headers'`、推奨の name「認証ページの Cache-Control (no-store なし)」。推奨文「ログイン後のページに `Cache-Control: no-store` を付ける」。
6. **`src/security/engine.ts`**: `SecurityEngine.evaluate` で `checkSubresourceIntegrity(input.url, input.dom?.sriResources)` と SEC-CACHE-01 の評価を呼び、`allChecks` に足す。
7. **`src/security/headers.ts`**: `SECURITY_HEADER_NAMES` に `'cache-control'` を足す（G5。`ALLOWED_RESPONSE_HEADERS` はここから作られる）。
8. **`src/background/service-worker.ts`**: `HEADER_DEPENDENT_CHECK_PREFIXES` に `'SEC-CACHE-'` を足す。`SEC-SRI-` と `SEC-COOKIE-` は足さない（ヘッダーに依存しない）。
9. **`docs/DETECTION_SPECIFICATION.md`**: §8.3（SRI・Cache-Control）と §8.4（Cookie）に 5 つの ID の判定・status・重大度を手で書く。
10. **`PRIVACY_POLICY.md`**: 取得するヘッダーに cache-control を足す記述と、「script・stylesheet の URL と integrity 属性の有無を端末内で確認する（値は集めない）」旨（G5。文面は人が承認するので、変更点を WORKLOG に書く）。テストはしない。

### テストが前提にしている公開 API

- `SecurityEngine`（`src/security/engine.ts`、既存）、`checkCookies`（`src/security/cookies.ts`、既存）
- `extractDomSignals`（`src/content/content-script.ts`、既存）の戻り値の `sriResources`（新規。要素は `{ kind, url, hasIntegrity }`）
- `executeInspection`・`ALLOWED_RESPONSE_HEADERS`・`filterAndSanitizeHeaders`・`HEADER_DEPENDENT_CHECK_PREFIXES`（`src/background/service-worker.ts`、既存）
- `saveReportToHistory`・`getAllHistoryReports`（`src/storage/history.ts`、既存）、`generateMarkdownReport`、`isRequiresAttention`、`lintReportPair`（既存）

新しいモジュール `src/security/sri.ts` と関数名は推奨（テストは直接呼ばない）。

## 外部の事実

## 実装の担当への注意

- **integrity の値を、どこにも保存しない**。content-script で値を変数に取らず、`hasAttribute` と空かどうかだけを見る。`sri.ts` は受け取った要素を結果やレポートにそのまま入れない（`integrity` キーが混ざった入力のテストあり）。`InspectionReport` に `sriResources` を足さない。
- **SEC-CACHE-01 の接頭辞**だけを `HEADER_DEPENDENT_CHECK_PREFIXES` に足す。`SEC-SRI-` を足すと、ヘッダー未観測のときに SRI が unknown になり、テストが落ちる。`SEC-COOKIE-` も足さない（Cookie は chrome.cookies で取得し、ヘッダーに依存しない）。
- 既存のテスト `tests/service-worker.test.ts` の「IMPL-02: キャッシュの origin がタブと異なる場合」は、認証系 Cookie（`laravel_session`）があり、ヘッダー未観測で要確認 0 を期待している。SEC-CACHE-01 が接頭辞で unknown になれば影響しない。ほかに、Cookie のモックで `requiresAttentionCount` の値を固定しているテストが落ちたら、テストを変えずに `.agy-out/result.json` に `needsTestChange: true` と理由を書く。
- `tests/review-v1.6.5-acceptance.test.ts` の SPEC-01 のテストは、ヘッダーも Cookie も無い入力で要確認 0 を期待している。認証系 Cookie が無ければ SEC-CACHE-01 は出ないので影響しない。
- 認証系の判定に**新しい分類を作らない**。`classifyCookieAdvanced` の `category === 'authentication'` をそのまま使う。CSRF の Cookie は対象外。
- SEC-COOKIE-EXPIRY は**秒**（`expirationDate`）と**ミリ秒**（`Date.now()`）の単位を取り違えない。
- SameSite=None で Secure なしの Cookie を指摘しない（D7）。`normalizeSameSite` を使う（`no_restriction` と `none` の両方を `'none'` にする）。
- 別サイトの判定は `determinePartyType`（PSL）を使う。`hostname` の末尾 2 ラベルで比べない（`co.jp` のテストあり）。一覧の照合はホスト名の完全一致（`endsWith` や `includes` で比べない。偽装ホストのテストあり）。
- 観測値の URL はクエリとフラグメントを除く。`observed` は UI で `escapeHtml()` を通している既存の表示を使い、新しく innerHTML に入れる箇所を作らない。
- 新しい重大度は最大 low（G4）。SEC-COOKIE-* の既存の指摘（HTTPONLY など）の重大度・条件は変えない。
- `npm run spec:generate` は §8 を作り直さないので、仕様書の §8.3・§8.4 に ID を手で書く。
- `src/security/domain-analyzer.ts` の PSL（`psl-rules.generated.ts`、`data/psl/`）は変えない。
