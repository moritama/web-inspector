# T06 設計メモ — CVE ごとの判定と表示・エクスポート

## 目的

Debian / Ubuntu でリリースが推定できた製品について、上流の照合で出た CVE（と、ディストリのデータにだけあって `not-fixed` になる CVE）ごとに、ディストリでの修正状況 `distroStatus`（§4.2 の 6 区分）を付ける。要確認件数とバッジを §4.2 の表（H4a）に合わせ、ポップアップ・ダッシュボード・Markdown / JSON / CSV に区分と修正版（JSON には OSV ID と出典も）を出す。あわせて、T03 で 4 か所に重複したリリースの表示名を作る処理を 1 か所にまとめ、リリース欄に上流の EOL ラベルが出ないようにする。判定はすべて Needs Review（H4）。

指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **「要確認件数」と「バッジ」。** このリポジトリでの要確認件数は `summary.requiresAttentionCount`（status が warning / fail の指摘の数。`summarizeSecurityChecks`）、バッジは拡張のアイコンの数字（`updateBadge` に要確認件数を渡す）。第1段階のディストリ版は `advisories: []` で指摘を作らないため、CVE は要確認件数に入っていなかった。H4a は「fixed と not-affected は外す。それ以外は件数に入れる」と決めているので、**数える区分の CVE が 1 件以上ある技術ごとに、新しい指摘 `SEC-DISTRO-CVE-<技術名の大文字>` を 1 件出す**（status `warning`、新しいチェックなので severity `low`）。CVE ごとに指摘を作らない（Apache 1 つで上流の CVE が数十件あると要確認件数が数十増え、「警告を増やしすぎない」に反するため）。技術ごとの CVE の内訳は `distroAdvisories.reviewCount` に持たせ、画面とエクスポートに出す。
2. **「数える（第1段階と同じ）」。** unknown-revision と no-data は、第1段階と同じく「バージョン番号だけでは断定できない Needs Review」として扱う、という意味に取る（区分の扱いを第1段階から変えない）。H4a の「それ以外は件数に入れる」により、上の 1. の指摘の数に入る。このため、**同梱 DB に `distro.advisories` がある状態では、Ubuntu / Debian の Apache・nginx（パッケージ版が取れない）でも、上流の CVE が 1 件以上あれば LOW の指摘が 1 件増える**（第1段階より要確認件数が増える）。H4a の決定どおりだが、件数が増えることは WORKLOG の未解決に書き、人の確認を求める。
3. **ディストリのデータが無い DB。** `distro` 節が無い、または `distro.advisories` が無い DB（T02 までの DB・固定 DB）では、CVE ごとの判定をしない（`distroAdvisories` を付けない。指摘も出さない）。§5.3「distro 節が無い DB でも第1段階の表示で動く」を、データの無い `advisories` にも当てはめる。既存のテストの期待値が変わらない。`advisories` はあるが、そのリリース×ソースパッケージのキーが無い（取得できなかった）ときは、その CVE は no-data（数える）。
4. **ディストリにだけある CVE。** §4.1 は「ディストリのデータにだけあって `not-fixed` になるもの」だけを照合の対象にしている。そのとおり、ディストリにだけある CVE は `not-fixed` のものだけ並べて数え、`fixed` は件数（`otherFixedCount`）だけ出す（§4.2）。ディストリにだけある `open`・`not-affected`・`unknown-revision`（パッケージ版が無い）・no-data は並べず、数えない。Ubuntu のデータには古い CVE の open（needs-triage・deferred など）が多く、全部を数えると要確認が大きく増えるため（未解決に記録）。
5. **区分の決め方（リリースごと）。** 対象のリリース R、ソースパッケージ S、データ `E = distro.advisories[R][S]`:
   - S が決められない、または E が配列でない → no-data
   - E にその CVE が無い → no-data
   - `status: 'not-affected'` → not-affected
   - `status: 'open'` → open
   - `status: 'fixed'`: パッケージ版が無い → unknown-revision。パッケージ版が**すべての** `fixedVersions` 以上（`compareDpkgVersions(pkg, fv) >= 0`）→ fixed。1 つでも小さい → not-fixed。比較できない（`compareDpkgVersions` が null）ものが 1 つでもあり、ほかに小さいものが無い → unknown-revision（断定しない）
   - 「すべての修正版以上」は T05 の解釈 3（修正版が複数あるとき並べ替えずに全部残し、T06 で決める）を受けた安全側の決め方。
6. **悪いほうの順。** not-fixed > open > unknown-revision > no-data > fixed > not-affected（左ほど悪い）。数える区分は数えない区分より必ず悪い。not-fixed（修正版があるのに古い）を open より悪いとするのは、版の比較で確かめた結果であり、更新で直せる指摘だから。採ったリリースが複数あれば候補の順で先のもの。
7. **表示名の共通化と、リリース欄の値。** `formatDistroReleaseDisplay` は、(1) `inf.release` があればその表示名、(2) 候補が 1 件以上で `eolInfo.source` が OS のライフサイクル（T03 の `judgeDistroEol` が付ける `'endoflife.date（OS のライフサイクル）'`）で `eolInfo.label` があれば label、(3) 候補が 1 件以上なら候補の表示名を ` / ` で連結、(4) それ以外（第三者・バックポート・none）は `推定なし`。指示書「`inf.release` を優先し、`eolInfo.label` は推定由来のときだけ使う」をこの順にした。T03 の `judgeDistroEol` の label の名前も同じ関数で作る（「1 か所だけ」）。
8. **upstream の CVE の取り方。** 上流の照合で出た CVE は、第1段階の `countUpstreamAdvisories` と同じ条件（ディストリ版の文字列から上流版を取り出し、`satisfiesVersionRange`）で一致した advisory の CVE ID。件数は `upstreamAdvisoriesCount` と一致させる（テストで確認）。`advisories`（技術の照合結果）は第1段階のまま空にして、`SEC-CVE` の指摘・`vulnerableLibraryCount` は変えない（H4。`Potentially Affected` にしない）。
9. **パッケージの版。** ヘッダーの製品トークンの直後が `-` で始まる接尾辞（`-4ubuntu2.19`、`-1+deb11u5`）のときだけ、`<上流版><接尾辞>` をパッケージ版とする。括弧内の OS 名だけ（Apache・nginx）では付けない。ヘッダーに epoch は出ないので、修正版に epoch があればパッケージ版は小さく比べられ not-fixed になる（数える側。安全側）。
10. **新しい指摘とヘッダー依存。** `SEC-DISTRO-CVE-` は Server・X-Powered-By に依存するので、規則どおり `HEADER_DEPENDENT_CHECK_PREFIXES` に足す（ライブラリの指摘はヘッダーが未観測なら作られないので、挙動は変わらない）。

export type DistroCveStatus = 'not-fixed' | 'open' | 'unknown-revision' | 'no-data' | 'fixed' | 'not-affected';

/** 候補のリリースごとの判定 (v1.8.1 T06 / §4.1) */

export interface DistroCveAssessment {
  cve: string;
  origin: 'upstream' | 'distro';  // 上流の照合で出た CVE か、ディストリのデータにだけある CVE か

  sourcePackage: string | null;
  fixedVersions: string[];         // 採ったリリースの修正版（dpkg の版）
  esm?: true;                      // Ubuntu Pro（ESM）だけの修正
  osvIds: string[];                // 元の OSV ID（採ったリリースのもの。無ければ []）

  // engine が上流の advisory から補ってよい表示用の項目（任意。テストは見ない）
  title?: string;
  severity?: string;

  family: DistroFamily;            // 'ubuntu' | 'debian'
  releases: string[];              // 照合したリリース（inference.candidates のまま）

  reviewCount: number;             // cves のうち counted の件数

### 4. 新規 `src/detection/distro-advisory.ts`

```ts
import { compareDpkgVersions } from '../security/dpkg-version';
import type { AdvisoryDistroSection, DistroAdvisoryAssessment, DistroInference, DistroProduct } from '../shared/types';

export interface AssessDistroAdvisoriesInput {
  product: DistroProduct;
  upstreamVersion: string;             // 上流版（tech.version。例 '7.4.3'）
  packageVersion: string | null;       // inference.packageVersion ?? null
  inference: DistroInference;
  upstreamCves: string[];              // 上流の照合で出た CVE ID（重複なし）
  distro: AdvisoryDistroSection | null | undefined;
}

/** CVE ごとにディストリの修正状況を判定する（§4）。判定しない入力では null */
export function assessDistroAdvisories(input: AssessDistroAdvisoriesInput): DistroAdvisoryAssessment | null;
```

- **`version-matcher` を import しない**（テストが確かめる）。版の比較は `compareDpkgVersions` だけ。
- null を返す: `distro` が null / undefined、`distro.advisories` がオブジェクトでない、`inference.thirdParty` がある、`inference.candidates` が空、`inference.family` が `'ubuntu'`・`'debian'` 以外（H1）。
- ソースパッケージ（リリース R ごと）: `distro.map` のうち `family === inference.family && release === R && product === input.product` の項目。`upstreamVersions` に `upstreamVersion` を含む項目があればその `sourcePackage`、無ければ項目のソースパッケージが 1 種類だけのときそれ、それ以外は null。
- 区分: 解釈 5。悪いほう: 解釈 6。候補が 1 件なら `perRelease` と `split` を付けない（付けるなら `split: false`）。2 件以上なら `perRelease` を候補の順で付け、区分が 1 つでも違えば `split: true`。
- 採った区分の `release`・`sourcePackage`・`fixedVersions`・`esm`・`osvIds` は、その区分を出したリリースのもの（同じ区分が複数なら候補の順で先）。
- 上流の CVE（`upstreamCves` の順）: 全件を `cves` に入れる（`origin: 'upstream'`）。
- ディストリにだけある CVE: 全候補の E に出てくる CVE のうち `upstreamCves` に無いものを、同じ規則で判定する（そのリリースに無ければ no-data）。採った区分が `not-fixed` なら `cves` に足す（`origin: 'distro'`、CVE ID の昇順）。`fixed` なら `otherFixedCount` を 1 増やす。それ以外は捨てる（解釈 4）。
- `counted`: not-fixed・open・unknown-revision・no-data は true、fixed・not-affected は false。`reviewCount` は `cves` の counted の数。
- `sources`: `distro._source` のうち `ecosystem` が `family` に対応する（ubuntu → `'Ubuntu'`、debian → `'Debian'`）要素の複製。`_source` が無ければ `[]`。
- `splitNote`（分かれた CVE が 1 つ以上のとき）: `候補のリリース（<候補の表示名を ' / ' で連結>）で結果が分かれたため、悪いほうの結果を採りました（<分かれた CVE を '、' で連結>）。`
- `message`（`fv` は採った修正版を ` / ` で連結したもの。ESM なら `（ESM で修正）` を続ける）:

| 区分 | 文言 |
| --- | --- |
| not-fixed | `パッケージの版（<pkg>）はディストリの修正版より古い可能性があります。<fv> 以上への更新を検討してください。` |
| open | `ディストリで未修正です（修正版はまだありません）。ディストリのセキュリティ情報を確認してください。` |
| unknown-revision | `パッケージの版が取れないため判定できません。<fv> 以上であれば、ディストリで修正済みの可能性が高いです。サーバー側でパッケージの版を確かめてください。` |
| no-data | `ディストリのデータにこの CVE がありません。セキュリティ修正がバックポートされている可能性があるため、バージョン番号だけでは断定できません。` |
| fixed | `ディストリで修正済みの可能性が高いです（修正版 <fv>）。` |
| not-affected | `ディストリは影響なしと判断しています。` |

  - テストは部分一致で、not-fixed に修正版と「更新」、open に「未修正」、unknown-revision に修正版と「サーバー」、no-data に「バックポート」、fixed に「ディストリで修正済みの可能性が高い」、not-affected に「影響なし」、ESM に「ESM で修正」を確かめる。
  - 「該当なし」「安全」「Not Affected」「影響はありません」を使わない（C18 は distro を含むファイル名・行の文字列を検索する）。

- `SEC-DISTRO-CVE-<技術>` は技術ごとに最大 1 件。CVE ごとやインスタンスごとに作らない。重大度は `low`（新しいチェックの上限）。
- 文言に「該当なし」「安全」「Not Affected」「影響はありません」を書かない（総合チェック C18 が、ファイル名か行に distro を含む `src/` の文字列を検索する）。「影響なし」は使ってよい（not-affected の要旨）。
- 値はすべてエスケープする（HTML は `escapeHtml()`、Markdown はコードスパンか `escapeMarkdownTableCell`）。ディストリのデータは同梱 DB の値だが、ヘッダー由来の `packageVersion` は MAIN world ではないものの外部の値なので必ず通す。
- 新しい型の項目は任意（`?`）。旧い履歴（`distroAdvisories` が無い）でも画面とエクスポートが壊れないこと。
- `tests/` と設計メモは変更しない。テストの期待値が仕様と合わないと考えたら、`.agy-out/result.json` に `needsTestChange: true` と理由を書く。
