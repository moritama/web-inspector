# T03 設計メモ — OS リリースの推定とライフサイクルによる EOL 判定

## 目的

第1段階（SPEC-02）で保持している Server・X-Powered-By の値から、製品ごとに OS のリリースを推定し（`distroInference`）、推定したリリースのサポート期間（endoflife.date 由来の `distro.releases`）で EOL を判定する。上流の版による EOL は参考表示にして数えない。推定の結果はすべて Needs Review とし、「該当なし」「安全」と断定しない（H4）。

## 仕様の解釈

受け入れ条件を、テストで確かめられる形に言い直す。

| # | 受け入れ条件・指示書 | テストで確かめる形 |
| --- | --- | --- |
| A1 | §3.1 の確信度の各行について、その確信度になる入力のテストがある | `inferDistroFromHeaders` に固定 DB の `distro` 節を渡し、high（パッケージ版の印 `+deb11u5`・`~deb12u1`・`.el9`・`.el9_4`／複数製品の積集合で 1 件）、medium（対応表で 1 製品から 1 件）、low（候補 2 件以上。nginx 1.18.0 の Ubuntu 20.04 と 22.04）、none（対応表に無い上流版）の入力で、それぞれの `confidence`・`release`・`candidates` になる |
| A2 | `deb.sury.org` を含む PHP の版と `~bpo` を含む版で、リリースを推定せず `thirdParty` が付く | 単体: `thirdParty` があり、`release: null`・`candidates: []`・`confidence: 'none'`。engine: PHP の技術に `distroInference.thirdParty` が付き、EOL は第1段階の照合結果のまま |
| A3 | 推定した結果がどれも Needs Review で、「該当なし」「安全」の文言が出ない | 推定の結果が付いた技術の `advisoryMatchStatus` が `Needs Review`、`supportStatus` が `Supported` でない（標準サポート中でも断定しない）。`distroInference`・`eolInfo`・`upstreamEolInfo`・EOL の指摘・ポップアップ・ダッシュボードの HTML に「該当なし」「安全」「Not Affected」が無い |
| A4 | OS の EOL と上流の EOL が二重に数えられない | OS の標準サポートが終わり、上流（PHP 7.4）も EOL のとき、PHP の `SEC-EOL-PHP*` はちょうど 1 件。OS がサポート中で上流だけ EOL のときは 0 件で、`eolCount` も 0。上流の EOL は `upstreamEolInfo` に参考として残る |
| A5 | `distro` 節が無い DB では、第1段階と同じ出力になる | 固定 DB から `distro` 節を外した旧 DB で、`distroInference`・`upstreamEolInfo` が付かず、`eolInfo`・`supportStatus`・`advisoryMatchStatus` が第1段階の `matchOfflineAdvisories(…, { distroHint })` と同じ。EOL の指摘も出ない。既存のテストの期待値は変えない |
| A6 | reports:lint が通る | 推定を含む調査結果（OS の EOL あり・なし）の JSON と Markdown の組が `lintReportPair` の全項目を通る |
| B1 | ポップアップ・ダッシュボード・Markdown / JSON / CSV に、推定したリリース・確信度・根拠を出す（§3.2） | `renderTechModalHtml`・`renderFullTechnologiesHtml`・`generateMarkdownReport` にリリース名（`Ubuntu 20.04`）・「推定」・「確信度」・根拠のヘッダーの値。`renderLibrarySecurityTableHtml`・CSV にリリース名と確信度。JSON に `distroInference` の各項目。第三者リポジトリの注記と「リリースを推定できない」注記も出る。根拠の値は HTML でエスケープされる |
| B2 | 候補が 1 件ならそのリリースで判定、2 件以上なら最も早く終わる候補で判定し全候補を併記（§3.2） | `judgeDistroEol` と engine で、終了日の翌日は EOL、当日・前日は EOL でない。2 件のときは終了日が早いほう（対応表の順ではない）の日付を `eolDate` にし、文言に両方のリリース名 |
| B3 | 文言の例・日付はデータから（§3.2） | 文言に推定・確信度（高・中・低）・データの日付・「延長されている可能性」が入る。テストは日付を直接書かず、固定 DB の日付か「今日」からの相対で作る |
| B4 | `docs/DETECTION_SPECIFICATION.md` に推定の規則と確信度の表を書く | 仕様書に `distroInference`・`deb.sury.org`・`+ubuntu`・`~bpo` と、行頭が `high`・`medium`・`low`・`none` の表の行がある |

指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **標準サポート中のときのサポート状況。** H4 により、推定にもとづいて「サポート中」と断定しない。標準サポートが終わっていれば `EOL`、終わっていなければ `Unknown`（`eolDate` には終了予定日を入れ、文言で「推定」と書く）。`Supported`・`Maintenance` にはしない。
2. **EOL の境界。** endoflife.date の `eol`（＝`standardSupportEnd`）はサポート最後の日として扱い、「今日（UTC の YYYY-MM-DD）> 終了日」のときだけ EOL とする（当日は EOL にしない）。
3. **重大度。** §3.2「重大度の区分は既存の EOL 判定（SPEC-04）に合わせる」により、推定の EOL も既存の `SEC-EOL-<技術>` と同じ status（`warning`）・severity（`medium`）にする。新しいチェック ID は作らない（LOW 上限は新しいチェックの規則で、これは既存の EOL 判定の延長）。
4. **二重に数えない範囲。** 製品ごとに「OS の EOL」と「上流の EOL」を両方数えない（製品ごとに EOL の指摘は最大 1 件）。同じ OS の上の別の製品（Apache と PHP）は、既存の SPEC-04 と同じく製品ごとに数える（OS 単位にまとめる指示は無い。未解決に記録）。
5. **上流の EOL を「参考として残す」。** 第1段階では、ディストリ版の製品の EOL は `Unknown`（上流の EOL は計算していない）。T03 では、候補が 1 件以上あり OS のライフサイクルで判定できた製品に限り、上流の版で既存の EOL 照合（SPEC-04）をした結果を `upstreamEolInfo` に入れ、「参考（上流のサポート期間）」と表示する。要確認件数・EOL 件数・`SEC-EOL` には使わない。候補が無い・第三者・ライフサイクルが無いときは第1段階の表示のまま（`upstreamEolInfo` を付けない）。
6. **ライフサイクルが無いとき。** `distro.releases` が空（T02 の取得前・取得失敗）か、候補のどれかにライフサイクル（`standardSupportEnd`）が無いときは、EOL を判定しない（第1段階のまま）。推定（`distroInference`）は付ける。候補の一部だけ日付が無いときに残りで判定すると、日付の無い候補のほうが早く終わる可能性を見落とすため。
7. **第三者・バックポートの印の範囲。** 指示書の「`deb.sury.org`、`+ubuntuNN.NN`、`~bpo` など」のうち、この 3 つだけを印にする（一次資料で形を確かめたもの）。PPA 一般（`~ppa` など）は確かめていないので印にしない（その場合は対応表に無ければ none になり、断定はしない）。
8. **Ubuntu の `~NN.NN`（例 `1.1.1-1ubuntu2.1~18.04.23`）。** リリースの印として使える可能性はあるが、一次資料で規則を確かめていないので、T03 ではリリースの印にしない（対応表で引く）。
9. **`.elN` の系統。** 同じヘッダーに RHEL 系の OS 名（CentOS・AlmaLinux・Rocky Linux・Red Hat Enterprise Linux）があればその系統、無ければ `rhel`。`.el9_4` のような RHEL のマイナーリリースの errata の印も `9` として扱う。
10. **`~bpo` の照合の区分。** `~bpo` の版は第1段階で `distroHint` が付かず、上流の版で照合される。T03 は「第三者・バックポートは第1段階の表示のまま」（§3.2）なので、照合の区分は変えない（A3 の Needs Review の検査の対象から外す。`thirdParty` と注記は付ける）。
11. **OpenSSL。** OpenSSL は検出する技術ではないが、§3.1 手順 3.3 の例（Apache と OpenSSL）のとおり、Server ヘッダーの `OpenSSL/<版>` を積集合の手がかりにする。推定の結果は `inferDistroFromHeaders` の戻り値の `openssl` に入るが、技術一覧には足さない。
12. **積集合の対象。** 候補が 1 件以上ある製品（パッケージ版の印から得たリリースを含む）だけで積集合を取る。候補が無い製品・第三者の製品は加えず、積集合の結果も受け取らない。積集合が 1 件なら参加した全製品を high、2 件以上なら low（印で high の製品は high のまま）、空なら各製品の候補のまま。
13. **旧 DB の扱い。** 照合 DB を差し替えた（`setTestAdvisoryDatabase`）とき、差し替えた DB に `distro` 節が無ければ、同梱 DB の `distro` 節で補わない（§5.3「`distro` 節が無い DB でも第1段階の表示」）。

### 2. 新規 `src/detection/distro-inference.ts`

テストが import する公開 API（名前と型をこのまま）:

```ts
import type { AdvisoryDistroSection, DistroInference, DistroProduct, EolInfo } from '../shared/types';

export interface DistroEolJudgement {
  basisRelease: string;   // 判定に使ったリリース（候補が 2 件以上なら最も早く終わるもの）
  eolInfo: EolInfo;
}

/** Server・X-Powered-By の値から製品ごとに OS リリースを推定する（§3.1）。distro が無ければ {} */
export function inferDistroFromHeaders(
  responseHeaders: Record<string, string[] | undefined>,
  distro: AdvisoryDistroSection | null | undefined
): Partial<Record<DistroProduct, DistroInference>>;

/** 推定したリリースのライフサイクルで EOL を判定する（§3.2）。判定できなければ null */
export function judgeDistroEol(
  inference: DistroInference,
  distro: AdvisoryDistroSection | null | undefined,
  now: Date
): DistroEolJudgement | null;
```

#### 2.1 `inferDistroFromHeaders` の手順

1. `distro` が null / undefined、または `distro.map` が配列でなければ `{}` を返す（§5.3）。
2. ヘッダー名は大文字小文字を区別せず、`server` → `x-powered-by` の順に、各ヘッダーの各値（先頭 200 文字）を見る。ほかのヘッダーは使わない（K3「すでに取得している Server・X-Powered-By の値だけ」）。
3. 値の中の製品トークンを `/([A-Za-z]+)\/(\d+(?:\.\d+)+[a-z]?)(\S*)/g` で拾う。名前（大文字小文字を区別しない）が `apache`・`nginx`・`php`・`openssl` のものだけを使う。上流版は 2 番目の組（例 `7.4.3`、`1.1.1f`）、パッケージ版の接尾辞は 3 番目の組（例 `-4ubuntu2.19`、`-1+deb11u5`）。同じ製品が 2 回出たら最初のものだけを使う。
4. 製品ごとに、次の順で判定する（印の一覧はテストで固定。下の表）。
   1. **第三者・バックポート（手順 2）**: 接尾辞に第三者の印があれば `thirdParty` を記録し、`release: null`・`candidates: []`・`confidence: 'none'`・`note`（第三者の文言）で終える。系統は分かれば入れる（`+ubuntu…` は `ubuntu`、`~bpo` は `debian`。分からなければ同じヘッダーの OS 名、それも無ければ null）。
   2. **系統（手順 1）**: 接尾辞の印（`ubuntuN` → ubuntu、`debNuM` → debian、`.elN` → 解釈 9）、無ければ同じヘッダーの値の括弧内の OS 名。どちらも無ければ、その製品には推定を付けない（戻り値にキーを作らない）。
   3. **パッケージ版のリリース（手順 3.1）**: `[+~]deb(\d+)u\d+` → `debian:<N>`、`\.el(\d+)(?:_\d+)*` → `<系統>:<N>`。あれば候補はその 1 件、確信度 high（対応表に無くても使う）。
   4. **対応表（手順 3.2）**: `distro.map` から `family`・`product`・`upstreamVersions` に上流版を含む項目の `release` を、重複を除いて対応表の順に集める。1 件 → medium、2 件以上 → low、0 件 → none（`note` に none の文言）。
5. **積集合（手順 3.3）**: 候補が 1 件以上ある製品（第三者を除く）が 2 つ以上あれば、候補の積集合を取る。空でなければ、参加した各製品の `candidates` を積集合にし、1 件なら `release` をそれにして確信度 high、2 件以上なら `release: null`・確信度 low（印で high の製品は high のまま）。各製品の `evidence` に、ほかの製品のヘッダー・トークンを足す（`detail` 例「同じ応答の別の製品の候補と突き合わせました」）。空なら何も変えない。
6. 戻り値は製品ごとの推定（`apache`・`nginx`・`php`・`openssl` のうち、推定を付けたものだけ）。

**印の一覧（テストで固定）:**

| 種類 | 印 | 結果 |
| --- | --- | --- |
| 括弧内の OS 名 | `(Ubuntu)`・`(Debian)`・`(Red Hat Enterprise Linux)`・`(CentOS)`・`(AlmaLinux)`・`(Rocky Linux)`（大文字小文字を区別しない） | 系統 ubuntu・debian・rhel・centos・almalinux・rocky |
| 対象外の OS 名 | `(Unix)`・`(Win64)`・`(Fedora)`・`(Amazon Linux)`、OS 名なし | 推定を付けない |
| パッケージ版 | `ubuntuN`（例 `-4ubuntu2.19`） | 系統 ubuntu（リリースは対応表で引く） |
| パッケージ版 | `+debNuM`・`~debNuM`（例 `-1+deb11u5`、`-1~deb12u1`） | 系統 debian、リリース `debian:N`、high |
| パッケージ版 | `.elN`・`.elN_M`（例 `-1.el9`、`-1.el9_4`） | 系統は解釈 9、リリース `<系統>:N`、high |
| 対象外のパッケージ版 | `.fcNN` など上記以外 | 推定を付けない |
| 第三者 | `deb.sury.org`、`+ubuntuNN.NN`（例 `+ubuntu20.04.1`） | `thirdParty: { kind: 'third-party' }`、推定しない |
| バックポート | `~bpoN`（例 `~bpo10+1`） | `thirdParty: { kind: 'backport' }`、推定しない |

`evidence` には、系統を決めた印（OS 名なら `token` に `(Ubuntu)` のような括弧つきの文字列）、パッケージ版の印（`+deb11u5` など）、第三者の印、対応表で引いたときの製品トークン（`Apache/2.4.41`、`OpenSSL/1.1.1f`）を入れる。`header` は小文字のヘッダー名、`value` はそのヘッダーの値（200 文字まで）。

#### 2.2 `judgeDistroEol` の手順

1. `inference.thirdParty` がある、`candidates` が空、`distro` が無い → `null`。
2. 各候補の `distro.releases` の項目を探す。どれかが無いか、`standardSupportEnd` が null → `null`（解釈 6）。
3. `standardSupportEnd` がいちばん早い候補を `basis` にする（同じ日なら候補の順で先のもの）。
4. `today = now.toISOString().slice(0, 10)`。`today > basis.standardSupportEnd` なら `status: 'EOL'`、それ以外は `status: 'Unknown'`（`Supported` にしない）。
5. 戻り値 `{ basisRelease: basis.release, eolInfo }`。`eolInfo` は次のとおり。

| 項目 | 値 |
| --- | --- |
| `status` | `'EOL'` または `'Unknown'` |
| `eolDate` | `basis.standardSupportEnd` |
| `source` | `'endoflife.date（OS のライフサイクル）'` |
| `sourceUrl` | `https://endoflife.date/<slug>`（slug: ubuntu→`ubuntu`、debian→`debian`、rhel→`rhel`、centos→`centos`、almalinux→`almalinux`、rocky→`rocky-linux`。T02 の catalog と同じ） |
| `label` | `<候補のリリース名を ' / ' で連結>（推定・確信度 <高・中・低>）` 例 `Ubuntu 20.04 LTS（推定・確信度 中）` |
| `note` | 終了: `<basis の名前>（推定・確信度 <c>）：標準サポートは <日付> に終了。<延長> で延長されている可能性があります。` 終了前: `<basis の名前>（推定・確信度 <c>）：標準サポートは <日付> まで（推定）。` 候補が 2 件以上なら末尾に `候補: <全候補の名前>。いちばん早く終わる <basis の名前> で判定しています。` |
| `recommendation` | 終了: `サポート中のリリースへの更新を検討してください。延長サポート（<延長>）を利用している場合は、その期限を確認してください。` 終了前: `サーバー側で OS のリリースとサポート期限を確認してください。` |

- リリース名: ubuntu `Ubuntu <cycle>`（`lts` が真なら末尾に ` LTS`）、debian `Debian <cycle>`、rhel `Red Hat Enterprise Linux <cycle>`、centos `CentOS <cycle>`、almalinux `AlmaLinux <cycle>`、rocky `Rocky Linux <cycle>`。
- 確信度の表示: high → 高、medium → 中、low → 低。
- 延長の名前: ubuntu → `ESM`、debian → `ELTS`、rhel → `ELS`、それ以外 → `ESM / ELS`（H4 の文言「ESM / ELS で延長されている可能性あり」）。
- 日付はデータの値をそのまま入れる。文言に日付・版を直接書かない。

**注記（`DistroInference.note`）の文言:**

- none: `リリースを推定できません（対応表に無い版です。自前ビルドや PPA の可能性があります）。`
- 第三者: `第三者リポジトリの版です（<marker>）。ディストリのデータでは判定しません。`
- バックポート: `Debian のバックポート（第三者リポジトリと同じ扱い）の版です（<marker>）。ディストリのデータでは判定しません。`

テストは「リリースを推定でき」「第三者リポジトリ」「推定」「確信度 高／中／低」「延長されている可能性」「参考」と、リリース名・日付を部分一致で確かめる（文言の一字一句には依存しない）。

### 3. `src/detection/advisory.ts`

- `AdvisoryDatabase` に `distro?: AdvisoryDistroSection;` を足す。
- `export function getActiveDistroSection(): AdvisoryDistroSection | null` を足す。**差し替えの DB（`setTestAdvisoryDatabase`）があればその `distro`（無ければ null）、無ければ同梱 DB の `distro`（無ければ null）。** 差し替えの DB に `distro` が無いとき、同梱 DB の値で補わない（解釈 13。既存の `{ ...advisoryDb, ...override }` の書き方をそのまま使うと同梱 DB の `distro` が残るので注意）。
- 上流の EOL の参考用に `export function matchUpstreamEol(technology: string, upstreamVersion: string): EolInfo` を足してよい（既存の非公開 `matchEolPolicy` を、差し替えの DB を考慮して呼ぶだけ。製品が無ければ `Unknown`）。名前はテストで使わない。
- `matchOfflineAdvisories` と既存の関数の挙動は変えない（既存テストと旧 DB の互換のため）。

### 4. `src/detection/engine.ts`

`detect()` で全技術の結果を作った後（return の直前）に、次を行う。

1. `const distro = getActiveDistroSection()`。null なら何もしない（第1段階と同じ出力。`distroInference`・`upstreamEolInfo` のキーも作らない）。
2. `inferDistroFromHeaders(input.network?.responseHeaders ?? {}, distro)` を 1 回だけ呼ぶ。
3. 技術名を製品に対応させる: `Apache` → apache、`Nginx` → nginx、`PHP` → php（`rule.id` の `apache`・`nginx`・`php` でもよい）。推定がある技術に `distroInference` を付ける。
4. `judgeDistroEol(inference, distro, new Date())` が null でなければ:
   - 上流の EOL を `upstreamEolInfo` に入れる（上流版での既存の EOL 照合。`label` か `note` の先頭に「参考（上流のサポート期間）」を付ける）。
   - 技術の `eolInfo`・`supportStatus`・`eolDate` を判定の結果にする。
   - **`instances` の各インスタンスの `eol`・`eolInfo`・`supportStatus`・`eolDate` も同じ値にする**（service-worker はインスタンスの `eol` を見て `SEC-EOL` を作る）。
5. `judgeDistroEol` が null（none・第三者・ライフサイクル無し）なら、EOL は第1段階のまま（`eolInfo` などを変えない）。`distroInference` は付ける。
6. `advisoryMatchStatus`・`advisories`・`distroHint` などは変えない。

### 5. `src/background/service-worker.ts`

- `SEC-EOL-<技術>` の作り方（status `warning`・severity `medium`・checkId・findingId）は変えない。製品ごとに最大 1 件（インスタンスが 1 つなら 1 件）になるので二重に数えない。
- 技術に `distroInference` があり、EOL がその判定によるとき（`eolInfo.source` で見分けるなど）は、指摘の `observed` か `description` に推定である旨（例「推定した OS（<label>）の標準サポートが終了しています」）を入れる。`recommendation` は `eolInfo.recommendation`。
- `upstreamEolInfo` は数えない（EOL 件数・要確認件数・指摘のどれにも使わない）。

## 実装の担当への注意

- **テストの日付:** テストは日付を直接書かない。合成 DB のライフサイクルは「今日」からの相対で作る。engine の判定は `new Date()`（調査した時点）で行う。`judgeDistroEol` は引数の `now` だけを使う（内部で `Date.now()` を呼ばない）。
- **旧 DB:** `setTestAdvisoryDatabase` で差し替えた DB に `distro` が無いときは、同梱 DB の `distro` で補わない（解釈 13）。`{ ...advisoryDb, ...override }` のままだと補ってしまう。
- **インスタンス:** `SEC-EOL` は service-worker がインスタンスの `eol` から作る。技術の `eolInfo` だけを変えると、指摘が出ない・数がずれる。
- **二重に数えない:** 上流の EOL（`upstreamEolInfo`）を `supportStatus`・インスタンスの `eol` に入れない。上流の EOL で別の `SEC-EOL` を作らない。
- **H4 と C18:** 総合チェック C18 は、`src/` のうちファイル名に `distro` を含むファイルの全行と、ほかのファイルの `distro` を含む行の文字列リテラルに「該当なし」「安全です」「安全と」「安全な状態」「Not Affected」「影響はありません」が無いことを検査する。推定の文言だけでなく、`distro` を含む行に既存の「収録 DB 上は該当なし」などを書き足さない。推定の結果の `supportStatus` を `Supported` にしない。
- **第1段階を変えない:** `matchOfflineAdvisories`・`detectDistroHint`・`distroHint`・`advisoryMatchStatus` は変えない。既存のテストの期待値（`Needs Review`・`Unknown Version`・上流版での参考件数）が前提にしている。
- **`~bpo`:** 第1段階で `distroHint` が付かない（照合の区分は変えない）。`distroInference.thirdParty` と注記だけを付ける。
- **受動的調査:** 推定に使うのは、すでに取得している Server・X-Powered-By の値だけ。追加のリクエストを送らない。`distro-inference.ts` は外部にアクセスしない。
- **MAIN world ではないが外部の値:** ヘッダーの値は相手のサーバーが決めるので、`evidence.value` は 200 文字で切り、表示では必ずエスケープする（テストが `<img …>` の値で確かめる）。
- **型:** 新しい項目はすべて任意（`?`）。旧い履歴（`distroInference` の無い技術）でも表示が壊れないようにする。
- **仕様書の生成:** `npm run spec:generate` が作る技術のカタログの部分を手で書き換えない。推定の節は生成の対象外の場所に書く（夜間はスクリプトが spec:generate を実行する）。
- **HEADER_DEPENDENT_CHECK_PREFIXES:** 新しいチェック ID は作らないので触らない（`SEC-EOL-` は既存。ヘッダー未観測なら推定も付かない）。
