# T07 設計メモ — NEW-03b CSP の追加項目

## 目的

CSP に、Trusted Types・upgrade-insecure-requests・form-action・report-to のレポート先の 4 項目を加える。評価は新しい `src/security/csp-extras.ts` に書き、`csp-parser.ts` の変更は呼び出しの数行（30 行以内）にとどめる。新しい指摘は最大 LOW（G4）で、CSP の問題点の表（Markdown 第 8 節）にも同じ表現で出す。

### 4 項目の判定

| 項目 | チェック ID | status / 重大度 | 問題点の表の指摘 ID | ディレクティブ |
| --- | --- | --- | --- | --- |
| Trusted Types | `SEC-CSPX-TT-01` | `info` / `info` | `CSP-TRUSTED-TYPES-MISSING` | `require-trusted-types-for` |
| upgrade-insecure-requests | `SEC-CSPX-UIR-01` | `info` / `info` | `CSP-UPGRADE-INSECURE-REQUESTS-MISSING` | `upgrade-insecure-requests` |
| form-action | `SEC-CSPX-FORM-01` | `warning` / `low` | `CSP-FORM-ACTION-MISSING` | `form-action` |
| レポート先 | `SEC-CSPX-REPORT-01` | `info` / `info` | `CSP-REPORT-TO-UNDEFINED-GROUP` | `report-to` |

「強制ポリシー」は `mode === 'enforce'` のポリシー（ヘッダーと meta）。ディレクティブ名は `parseCSPPolicy` が小文字にしているので、名前は大文字・小文字を区別しない（`Form-Action` も「ある」）。

- **SEC-CSPX-TT-01**: 強制ポリシーが 1 つ以上あり、どの強制ポリシーにも、値に `'script'`（大文字・小文字を区別しない）を含む `require-trusted-types-for` が無いとき。
  - `trusted-types` だけ、または値の無い `require-trusted-types-for` は「ない」扱い（仕様上、強制する対象が無いため）。
  - 強制ポリシーが無いとき（CSP なし、Report-Only だけ、meta の Report-Only だけ）は出さない（表の条件「強制の CSP があり」）。
  - meta の強制ポリシーでの指定は有効（CSP3 が meta で無効とするのは report-uri・frame-ancestors・sandbox だけ。外部の事実 1）。
- **SEC-CSPX-UIR-01**: 混在コンテンツが検出されていて（`context.mixedContentDetected === true`）、どの強制ポリシーにも `upgrade-insecure-requests` が無いとき。
  - `upgrade-insecure-requests` は値を持たない。`parseCSPPolicy` は `directives['upgrade-insecure-requests'] = []` を作るので、**キーがあるかどうか**で判定する（値の数で判定しない）。
  - Report-Only での指定は仕様上無視されるので数えない（外部の事実 2）。meta の強制ポリシーでの指定は有効（外部の事実 1）。
  - **CSP がまったく無いときも出す**。指示書の表は、他の 3 項目では「強制の CSP があり」と書き、この項目では書いていないため、条件を足さない。重大度は info で、警告は増えない。
  - 混在コンテンツは、content-script が https のページでだけ集める（`domSignals.mixedContent`）。SW は `domSignals.mixedContent.length > 0` を `mixedContentDetected` にする。
- **SEC-CSPX-FORM-01**: 強制ポリシーが 1 つ以上あり、どの強制ポリシーにも `form-action` が無いとき。`default-src` にフォールバックしない（`default-src 'none'` だけでも出す。外部の事実 3）。`form-action 'none'` は「ある」。
- **SEC-CSPX-REPORT-01**: **ヘッダーで受け取ったポリシー**（`source === 'response-header'`、強制と Report-Only の両方）のうち、`report-to` の値（最初のトークン）のグループ名が、Reporting-Endpoints ヘッダーの Dictionary のキーに無いものが 1 つ以上あるとき。
  - 未定義のグループが複数あっても 1 件にまとめ、observed か description に**未定義のグループ名をすべて**書く（判定根拠）。定義済みのグループ名は書かなくてよい。
  - Report-Only のポリシーも対象にする。この項目は防御の能力ではなく「レポートが届くか」の確認なので、積集合（B1）は当てはまらない。Report-Only で report-to を使う構成はよくあり、届かないと意味が無いため。
  - meta のポリシーは対象にしない（B2）。
  - `report-to` が無いポリシー（`report-uri` だけ、どちらも無い）は対象にしない。
  - Reporting-Endpoints が無い（`context.reportingEndpoints` が空か undefined）ときは、すべてのグループが「定義されていない」。
  - Reporting-Endpoints の解析: 複数行は `,` でつないでから RFC 9651 の Dictionary として読み、キー（lcalpha か `*` で始まり、lcalpha・数字・`_`・`-`・`.`・`*` が続く）を集める。前後の空白は捨てる。値（文字列の URL）の中身は検査しない（テストもしない）。解析できない値は、仕様上ヘッダー全体が無視されるので「定義なし」として扱ってよい（テストしない）。
  - 旧式の `Report-To` ヘッダー（Reporting API v0）だけで定義されたグループの扱いは、表に無いので見ない。Chrome は Reporting-Endpoints に対応した版では Reporting-Endpoints を使う（外部の事実 4）。指摘は info にとどまる。

### 問題点の表（ポリシーごと）に出す条件

`evaluateCspExtraIssues(policy, allPolicies, context)` が、そのポリシーの表に足す指摘を返す。

- TT・UIR・FORM: 対象のポリシーが**強制ポリシー**で、上の判定がページ全体で発火するとき（積集合なので、発火するときはどの強制ポリシーにも指定が無い）。強制ポリシーが複数あれば、その全部の表に出る。Report-Only のポリシー（ヘッダー・meta）の表には出さない。
- REPORT: 対象のポリシーがヘッダーのポリシー（強制・Report-Only）で、そのポリシーの report-to のグループが未定義のとき、そのポリシーの表にだけ出す。description にはそのポリシーのグループ名を書く。
- meta の Report-Only のポリシーの表には、新しい指摘を出さない。
- 「同じ表現」: 指摘の `severity` と `description` は、診断の項目（`SecurityCheckResult`）の `severity` と `description` と同じ文字列にする。REPORT は、未定義のグループが 1 つのとき同じ文字列になる（テストする）。複数のときは、診断の項目にすべて、表の各行にそのポリシーのグループ名が入る（テストする）。
- 文脈（`context`）を渡さないときは、新しい指摘を足さない（後方互換。既存の `tests/markdown.test.ts` は文脈の無いレポートで「このポリシーに検出された問題点はありません。」を期待している）。

### ヘッダー未観測のとき（SPEC-01）

- 新しい ID の接頭辞 `SEC-CSPX-` を `HEADER_DEPENDENT_CHECK_PREFIXES` に足す。未観測のときは既存のループが unknown / info に書き換える。meta の CSP があっても、ヘッダーの CSP に指定がある可能性を否定できないので、**meta の例外（`SEC-CSP-` だけ）を広げない**（断定しない）。
- 未観測のときは、Markdown 第 8 節の表にも新しい行を足さない（診断の項目が unknown なのに表で指摘すると矛盾するため）。

### テストでは問わないこと（実装に任せる）

- 文言の一字一句（ID・重大度・ディレクティブ名・グループ名を除く）、項目名（name）、referenceUrls、配列の順番
- `report-to` に複数のトークンがあるときの扱い（推奨: 最初のトークン）、グループ名の大文字・小文字
- `'script'` を大文字で書いたときの扱い（推奨: 区別しない）
- 合格の項目（例: SEC-CSPX-TT-00）を作るかどうか（推奨: 作らない。作るなら info）
- Reporting-Endpoints が解析できないときの扱い

## 実装の方針

1. **新規 `src/security/csp-extras.ts`**（公開 API。テストが直接呼ぶ）
   ```ts
   import type { CSPIssue } from './csp-parser';
   import { CSPPolicy, SecurityCheckResult } from '../shared/types';

   /** CSP の追加項目（v1.8.0 T07）の評価に使う、CSP 以外の観測結果 */
   export interface CspExtrasContext {
     /** DOM で混在コンテンツが 1 件以上検出されたか */
     mixedContentDetected: boolean;
     /** Reporting-Endpoints ヘッダーの値（受け取った行のまま）。ヘッダーが無ければ空配列か undefined */
     reportingEndpoints?: string[];
   }

   /** ページ全体の 4 項目（SEC-CSPX-*）を評価する。発火しない項目は返さない */
   export function checkCspExtras(
     policies: CSPPolicy[],
     url: string,
     context: CspExtrasContext
   ): SecurityCheckResult[];

   /** 1 つのポリシーの「問題点の表」に足す指摘を返す（id は CSP-TRUSTED-TYPES-MISSING など） */
   export function evaluateCspExtraIssues(
     policy: CSPPolicy,
     allPolicies: CSPPolicy[],
     context: CspExtrasContext
   ): CSPIssue[];
   ```
   - `checkCspExtras` は新しい 4 つの ID 以外を返さない。`category` は `http-headers`、`scope` は `url`。
   - `CSPIssue` の `directive` はディレクティブ名（上の表）、`policyId` は対象のポリシーの id、`pattern` は `'未指定'` や グループ名など。
   - description と recommendation は 1 か所（定数か関数）で作り、診断の項目と表の指摘で同じ文字列を使う。
   - 推奨の name: `CSP (Trusted Types)`、`CSP (upgrade-insecure-requests)`、`CSP (form-action)`、`CSP (report-to のレポート先)`。
   - 推奨文の方針: TT は「`require-trusted-types-for 'script'` を Report-Only で試してから強制を検討」。UIR は「混在コンテンツの URL を https に直す。すぐに直せない場合の補助として `upgrade-insecure-requests` を検討」。FORM は「`form-action 'self'`（送信先を限定）を指定。default-src では代替されない」。REPORT は「Reporting-Endpoints ヘッダーに同じ名前の送信先を定義するか、report-to の値を直す」。
   - `csp-parser.ts` から型を import するときは `import type` にする（循環 import を避ける）。
   - ポリシーの `directives` が空で `rawValue` だけのもの（保存された古いデータ）に備えるなら、`parseCSPPolicy(rawValue, source, mode)` で補ってよい（`ensureParsedPolicy` は非公開なので、同じことをこのファイルで行う）。
2. **`src/security/csp-parser.ts`**（**差分は 30 行以内**）

   - **`analyzeCSPPolicies`・`evaluateSinglePolicy`・`filterEnforceIssuesByIntersection`・`summarizeCSPIssues` は変えない**。新しい指摘を SEC-CSP-03 の集計・要約に入れると、既存の csp-parser.test.ts（SEC-CSP-00 の合格、`issues` の件数、要約の文字列）が落ちる。
3. **`src/background/service-worker.ts`**
   - `HEADER_DEPENDENT_CHECK_PREFIXES` に `'SEC-CSPX-'` を足す。
   - 5.1 の CSP の評価の後（`if (cspPolicies.length > 0)` の**外**。UIR は CSP が無くても出るため）、SPEC-01 の書き換えより**前**に、

## 外部の事実

1. **meta の CSP で無効なもの**: 「The Content-Security-Policy-Report-Only header is not supported inside a meta element.」「Neither are the report-uri, frame-ancestors, and sandbox directives.」。require-trusted-types-for・upgrade-insecure-requests・form-action はこの一覧に無いので、meta の強制ポリシーでも有効として扱う。なお report-to もこの一覧に無いが、既存の扱い（meta では無効）は指示書どおり変えない。
   - https://w3c.github.io/webappsec-csp/#meta-element （§3.3）、https://w3c.github.io/webappsec-csp/#cspro-header （§3.2）（2026-11-12 確認）
2. **upgrade-insecure-requests と Report-Only**: 「Monitoring the upgrade-insecure-requests directive has no effect: the directive is ignored when sent via a Content-Security-Policy-Report-Only header.」
   - https://w3c.github.io/webappsec-upgrade-insecure-requests/#delivery （§3.1）（2026-11-12 確認）
3. **form-action は default-src にフォールバックしない**: default-src の説明は「when default-src is set, every fetch directive that isn't explicitly set will fall back to the value default-src specifies」で、フォールバックはフェッチ用のディレクティブに限られる。form-action は「6.4 Navigation Directives」にあり、フェッチ用のディレクティブではない。指示書も「default-src にフォールバックしない」と明記している。
   - https://w3c.github.io/webappsec-csp/#directive-default-src 、 https://w3c.github.io/webappsec-csp/#directives-navigation （2026-11-12 確認）
4. **Reporting-Endpoints と report-to**: 「Reporting-Endpoints is a Dictionary Structured Field [STRUCTURED-FIELDS]. Each entry in the dictionary defines an endpoint to which reports may be delivered. The entry value MUST be a string.」。ヘッダーの解析結果が null なら処理を中止する（「If parsed header is null, abort these steps.」）。名前の付いた送信先が無いレポートは捨てられる（§3.5.1「Otherwise, remove report from reports.」）。report-to のようにエンドポイントを名前で参照する値は sf-token にすべき（SHOULD）とされる。CSP の違反レポートの送信先は「report-to directive's value」。
   - https://w3c.github.io/reporting/#header （§3.2）、https://w3c.github.io/reporting/#process-header （§3.3）、https://w3c.github.io/reporting/#send-reports （§3.5.1）、https://w3c.github.io/webappsec-csp/#directive-report-to （2026-11-12 確認）
   - Chrome の移行ガイド: 「Browser instances that support Reporting-Endpoints will use Reporting-Endpoints, and instances that don't will fallback to Report-To.」。旧式の Report-To だけで定義した名前が新しい Chrome で使われるかは、明記が無く**未確認**。指示書の表どおり Reporting-Endpoints だけを見る（指摘は info）。
   - https://developer.chrome.com/blog/reporting-api-migration （2026-11-12 確認）
5. **Trusted Types**: 「The require-trusted-types-for directive specifies the injection sinks groups, for which the types should be required.」「Guarding DOM XSS injection sinks is controlled by the trusted-types-sink-group named 'script'.」。例は `Content-Security-Policy: require-trusted-types-for 'script'`。ABNF の原文は確認できなかった（**未確認**）ため、値の大文字・小文字の扱いはテストしない。
   - https://w3c.github.io/trusted-types/dist/spec/ （§2.4.1、§4.2.1）（2026-11-12 確認）

## 実装の担当への注意

- **既存の SEC-CSP-00 / SEC-CSP-03 を変えない**。新しい指摘を `evaluateSinglePolicy` や `analyzeCSPPolicies` の `issues`・`results` に入れない。`tests/csp-parser.test.ts` には、form-action や Trusted Types の無い CSP で SEC-CSP-00（合格）、`results.length === 1`、`issues` の info 以外が 0 件、`summarizeCSPIssues` の文字列の完全一致を期待するテストが多数ある。
- **ID の接頭辞は `SEC-CSPX-`**（`SEC-CSP-` ではない）。`SEC-CSP-` にすると、SW の 5.1 の置き換え・SPEC-01 の meta の例外・csp-parser.test.ts の `startsWith('SEC-CSP-')` の件数・report-lint の CSP の重大度の検査に巻き込まれる。

- **upgrade-insecure-requests は値が空の配列**になる。`getDirectiveValuesWithFallback` や `directives[name]?.length` で判定すると「無い」と誤る。キーの有無で判定する（テストあり）。
- **checkCspExtras は SW で 1 回だけ呼ぶ**。`checkHttpHeaders`（SecurityEngine）でも足すと重複する（テストあり）。CSP が無くても呼ぶ（UIR）。

- `evaluatePolicyIssuesWithIntersection` は Report-Only のとき早く return する。REPORT の指摘を Report-Only の表にも出すため、その経路でも足す。
- csp-parser.ts の差分は**追加＋削除で 30 行以内**（`git diff --numstat a5bd583`）。コメントも数える。
- 新しい重大度は最大 low（G4）。FORM は `warning` / `low`（要確認に入る）、他の 3 つは `info` / `info`。
