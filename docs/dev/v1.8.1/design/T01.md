# T01 設計メモ — dpkg の版比較

## 目的

第3段階（CVE ごとの判定、T06）で「パッケージの版」と「ディストリの修正版」を比べるために、Debian Policy 5.6.12 と dpkg の実装に従う版の解析と比較の関数を新しく作る。上流の版比較（`version-matcher.ts`）とは別の関数にし、既存の挙動は変えない。

## 仕様の解釈

受け入れ条件を、テストで確かめられる形に言い直す。

| # | 受け入れ条件 | テストで確かめる形 |
| --- | --- | --- |
| A1 | dpkg 自身のテスト（`lib/dpkg/t/t-version.c`）の比較例を、出典を書いて取り込み、すべて成り立つ | `test_version_compare()`・`test_version_parse()`・`test_version_relate()` の各ケースを、同じ意味の版の文字列に書き直して表にする。比較は期待の符号（-1 / 0 / 1）になり、逆順では符号が反転する。解析に成功するケースは epoch・upstream・revision が一致し、失敗するケースは `null` |
| A2 | `7.4.3-4ubuntu2.19 > 7.4.3-4ubuntu2.2`、`1:1.0 > 2.0`、`1.0~rc1 < 1.0`、`2.4.62-1~deb11u1 < 2.4.62-1~deb12u1` | それぞれ `compareDpkgVersions(a, b)` が 1 / 1 / -1 / -1、逆順で反転 |
| A3 | 不正な入力（空、数字以外で始まる上流版、不正な epoch）で null | `parseDpkgVersion` が `null`、`compareDpkgVersions` はどちらかが不正なら `null` |
| — | 「既存の `isLinuxPackageVersion` と version-matcher の挙動は変えない」 | 代表的な入力で、現在の戻り値（実装前に実測した値）が変わらないこと。既存の `tests/version-check.test.ts` などもそのまま通ること |

指示書が曖昧な点と、どう解釈したか。

1. **t-version.c の比較は文字列ではなく「組」で書かれている。** `DPKG_VERSION_OBJECT(epoch, "upstream", "revision")` は `epoch:upstream-revision` と同じ意味の文字列に書き直した。次の 2 つは書き直せないので、意味を保って入力を変えた（テストのコメントにも書いた）。
   - `dpkg_version_blank()`（版が空）どうしの比較: 空の版は文字列にすると「空の入力＝null」（A3）になる。比較 2 件のうち「空どうしは等しい」は取り込まず、「epoch 1 と 2 は等しくない」は upstream を `0` にして `1:0 < 2:0` とした。
   - upstream が `"a"`・`"b"` の比較: 数字以外で始まる upstream は A3 で null にするので、先頭に `0` を付けて `0a-0 < 0b-0` とした（「upstream の部分の違いで決まる」という意図は同じ）。
   - t-version.c が「等しくない」とだけ書いているケース（`test_fail(compare == 0)`）は、規則から決まる符号（-1）で確かめる。
2. **upstream のコロン。** Debian Policy 4.7.4.1 の 5.6.12 は upstream に使える文字を「英数字と `.` `+` `-` `~`」としているが、dpkg の実装とテストは epoch があるときの upstream のコロンを受け付ける（`0:0:0-0` → upstream `0:0`）。A1 は dpkg のテストがすべて成り立つことを求めているので、**dpkg の実装に合わせ**、upstream にコロンを許す（最初のコロンまでが epoch なので、コロンを含む upstream は epoch があるときだけ現れる）。比べる対象はディストリが dpkg で作った版なので、この違いで判定が甘くなることはない。
3. **「数字以外で始まる上流版」。** Policy は「should start with a digit」だが、dpkg の `parseversion` は失敗を返す（t-version.c の `0:abc3-0`）。A3 のとおり null にする。
4. **前後の空白。** dpkg は前後の空白を無視し、途中の空白は不正とする（t-version.c）。同じにする。空白だけの入力は空と同じく null。
5. **epoch の上限。** dpkg は epoch が int の上限（2147483647）を超えると失敗する（t-version.c の「huge epoch」）。同じ上限にする。テストは巨大な値（24 桁）だけで確かめ、境界の値は確かめない（dpkg の実装の細部のため）。
6. **revision が無いとき。** `parseDpkgVersion` は `revision: ''`（空文字）を返す。t-version.c の `DPKG_VERSION_OBJECT(0, "0", "")` と同じ。比較では Policy のとおり revision `0` と等しい（`2.0` と `2.0-0` は等しい）。
7. **null / undefined の入力。** ヘッダー由来の値を渡す想定なので、引数の型は `string | null | undefined` とし、文字列以外は null を返す（例外を投げない）。
8. **戻り値の範囲。** 比較は -1 / 0 / 1 だけを返す（dpkg の内部の「差の値」を返さない）。数字の部分は桁数に関係なく正しく比べる（dpkg の `verrevcmp` は数字を 1 文字ずつ比べるので、桁の多い数でもあふれない。JavaScript の Number に変換すると精度が落ちるので、変換しない）。
9. **解析の戻り値の余分な項目。** テストは `toMatchObject` で `epoch`・`upstream`・`revision` だけを確かめる。ほかの項目（元の文字列など）を足してもよいが、必要はない。

## 実装の方針

### 変更するファイル

- 新規: `src/security/dpkg-version.ts`（これだけ）
- 変更しない: `src/security/version-matcher.ts`、`src/detection/advisory.ts`（T01 では呼び出し元を作らない。使うのは T06）

### 公開 API（テストが前提にしている名前と型）

```ts
/** 解析済みの dpkg の版 */
export interface DpkgVersion {
  /** epoch（省略時 0）。0〜2147483647 の整数 */
  epoch: number;
  /** upstream_version（必ず数字で始まる） */
  upstream: string;
  /** debian_revision（無いときは空文字 ''） */
  revision: string;
}

export function parseDpkgVersion(s: string | null | undefined): DpkgVersion | null;

/** a < b なら -1、等しければ 0、a > b なら 1。どちらかを解析できなければ null */
export function compareDpkgVersions(a: string | null | undefined, b: string | null | undefined): -1 | 0 | 1 | null;
```

`DpkgVersion` の名前はテストでは使っていない（型の名前は変えてもよい）。関数の名前・引数・戻り値はテストが使う。

### 解析の手順（`parseDpkgVersion`）

dpkg の `parseversion()` に合わせる。

1. 文字列でなければ null。
2. 前後の空白（スペースとタブだけ。dpkg の `c_isblank`）を取り除く。残りが空なら null。途中にスペースかタブがあれば null。改行などほかの制御文字は取り除かず、手順 6 の文字の検査で null になる。
3. 最初の `:` があれば、その前を epoch とする。epoch は 1 文字以上の数字（`[0-9]+`）だけで、2147483647 以下であること。そうでなければ null（空・負号・文字・小数点・巨大な数）。先頭の 0 はよい（`01` は 1）。epoch の後ろを残りとする。`:` が無ければ epoch は 0。
   - dpkg は epoch を `strtol` で読むので `+1:` や `-0:` も受け付けるが、Policy は「符号なし整数」としている。安全側（判定できないものは null）に倒し、数字だけを許す。テストはこの違いを確かめない。
4. 残りの**最後の** `-` で upstream と revision に分ける。`-` が無ければ revision は `''`。`-` があって revision が空なら null（`1.0-`）。
5. upstream が空なら null（`-0`、`0:-0`、`0:`）。upstream の先頭が数字でなければ null。
6. upstream に使える文字は `[0-9A-Za-z.+~:-]`、revision に使える文字は `[0-9A-Za-z.+~]`。それ以外を含めば null。
7. `{ epoch, upstream, revision }` を返す。

### 比較の手順（`compareDpkgVersions`）

1. 両方を `parseDpkgVersion` で解析し、どちらかが null なら null。
2. epoch を数として比べる。違えばその符号。
3. upstream を下の `verrevcmp` で比べる。0 でなければその符号。
4. revision を `verrevcmp` で比べる（空文字は「0」と同じ結果になる）。その符号。
5. 結果は -1 / 0 / 1 に丸めて返す。

`verrevcmp(a, b)`（dpkg の `lib/dpkg/version.c` と Policy 5.6.12 の手順。文字の順序 `order(c)` を使う）:

- `order(c)`: 文字列の終わり → 0、`~` → -1、数字 → 0、英字（A-Z, a-z）→ その文字コード、それ以外の記号 → 文字コード + 256。これで「`~` は終わりよりも前」「英字はすべての記号より前」「英字どうしは ASCII 順（`Z` < `a`）」になる。
- 両方の文字列が尽きるまで繰り返す:
  1. **数字でない部分**: どちらかの現在の文字が「終わりでなく、数字でもない」あいだ、`order` を比べ、違えば `order(a) - order(b)` を返す。両方を 1 文字進める。
  2. **数字の部分**: 両方の先頭の `0` を読み飛ばす。両方が数字のあいだ、最初に違った文字の差を覚えて進める。そのあと a だけにまだ数字が残っていれば 1（a の桁が多い）、b だけに残っていれば -1。どちらにも残っていなければ、覚えた差があればそれを返す。
- 尽きたら 0。

数字の部分を `parseInt` や `Number` で変換しないこと（桁の多い数のテストが落ちる）。

## 実装の担当への注意

- **`src/security/version-matcher.ts` を変えない。** `isLinuxPackageVersion`・`compareVersions` などは、ディストリの印を区別しない上流の比較のまま（テストの最後の describe が現在の値を固定している）。dpkg の比較を version-matcher に混ぜたり、version-matcher から呼んだりしない。
- **呼び出し元を作らない。** advisory の照合で使うのは T06。T01 では `advisory.ts` などを変えない。
- 数字の部分を `parseInt`・`Number`・`BigInt` に変換して比べない。文字列のまま 1 文字ずつ比べる（桁の多い数のテストがある）。epoch だけは数に変換してよい（上限 2147483647 を超えたら null）。
- 比較の戻り値は必ず -1 / 0 / 1 / null。`order` の差をそのまま返さない。
- 解析に失敗しても例外を投げない（null を返す）。
- 正規表現の文字クラスで `-` を使うときは末尾に置くなど、範囲の指定にならないよう注意する（upstream の `[0-9A-Za-z.+~:-]`）。
- 新しいセキュリティチェックではないので、`HEADER_DEPENDENT_CHECK_PREFIXES`・チェック ID・ルール JSON・検出仕様書は変えない（`spec:generate` の差分は出ないはず）。
- テストのファイル名・期待値は変えない。合わないと考えたら `.agy-out/result.json` に `needsTestChange: true` と理由を書く。
