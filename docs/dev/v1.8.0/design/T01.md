# T01 テストの点検 — 設計メモ

## 目的

DB だけの自動リリース（manifest の版に 4 つ目の番号が付く・同梱 DB の中身が変わる）でテストが落ちないよう、テストから版の文字列と同梱 DB の中身への依存をなくし、今後も書けないように test-hygiene で検査する。

## 仕様の解釈

指示書 §4 T01 の各項目を、テストで確かめられる形に言い直す。

| # | 指示書 | 解釈（テストで確かめること） |
| --- | --- | --- |
| A1 | 版の期待値は package.json から取り、比較は `isSameRelease(manifestVersion, pkgVersion)` で行う。判定は「3 要素が一致し、4 つ目は無いか数字だけ」 | `pkgVersion` は「数字.数字.数字」に限る（それ以外は false）。`manifestVersion` は 3 要素か 4 要素で、全要素が数字だけ、先頭 3 要素が `pkgVersion` と一致すれば true。5 要素以上・空の要素・プレリリース風の表記・前方一致だけ（`3.4.50` と `3.4.5`）は false |
| A2 | spec-integrity.test.ts の `targetVersion = '1.7.1'` と advisory-db-invariants.test.ts の manifest の版を置き換える | 両ファイルの manifest の版の確認を `isSameRelease(manifest.version, readPackageVersion())` にする。spec-integrity の「package.json / manifest / HTML / README の版」のテストの、manifest との比較（自前の分割）も同じ関数に揃える |
| A3 | minExtensionVersion の `'1.7.0'` は、catalog など値の出どころと比べる | 値の出どころは `scripts/advisories/build-db.mjs` の `MIN_EXTENSION_VERSION`（DB の生成時にそのまま書き込まれる）。`advisoryDb.minExtensionVersion === MIN_EXTENSION_VERSION` を確かめる。同様に schemaVersion は `OUTPUT_SCHEMA_VERSION`、製品の一覧は `data/advisories/catalog.json` の `products` のキー（catalog.json に「キーは advisory-db.json の libraries キーと一致させる」とある）と比べる |
| A4 | 検出・照合のテストは固定 DB を既定にする。setupFiles で `setTestAdvisoryDatabase` を呼ぶ | setup ファイル `tests/setup/advisory-db.ts`（設計とテストの担当が作成済み）を `vite.config.ts` の `test.setupFiles` に入れる。確かめること: (a) vite.config.ts に指定がある、(b) DB を渡さずに照合すると固定 DB の dataVersion・収録件数が使われる、(c) 明示的に渡した DB は既定より優先される、(d) あるテストで `setTestAdvisoryDatabase(null)` を呼んでも次のテストでは固定 DB に戻る |
| A5 | 同梱 DB を読んでよいのは許可リストのファイルだけ | 許可リストは `tests/advisory-db-invariants.test.ts` の 1 件だけにする（spec-integrity が読んでいた minExtensionVersion の確認は invariants に移した）。「読む」とは、静的・動的 import／require の指定子、`path.join` の部品としてのファイル名だけの文字列、`readFileSync`・`new URL`・`join`・`resolve` などの呼び出しの引数（複数行でもよい）に `advisory-db.json` が現れること。`changedFiles` の配列にパスとして書くだけ（advisory-pipeline.test.mjs）は「読む」に当たらない。固定 DB（`advisory-db.fixture.json`）は該当しない |
| A6 | 同梱 DB を読むテストも、件数・日付・特定の CVE の有無を直接比べない | advisory-db-invariants.test.ts から、収録件数の下限（350 件）・特定の CVE（Apache 2.4.52 の CVE）・`minExtensionVersion` の直書き・版の正規表現の直書きを外す。同梱 DB で確かめるのは、スキーマ・書式・range の構文・出どころとの一致・`getAdvisoryDbMetadata()` が同梱 DB の値をそのまま返すこと（整合）だけ。照合の挙動（Apache の該当・Ubuntu 版の Needs Review）は固定 DB で確かめる |
| A7 | test-hygiene (1)(2) を追加する | (1) 許可リスト外のテストのソース（`tests/` 以下の `.ts` `.mts` `.cts` `.js` `.mjs` `.cjs` など。`tests/fixtures/snapshots/` は対象外）に同梱 DB を読む箇所が 0 件。(2) 許可リスト外のテストのソースに、現在の package.json の版の文字列が 0 件。「版の文字列」とは、引用符（' " `）で囲まれた中身が「版」「v版」またはそれに 4 つ目の数字が付いたもの、および正規表現でエスケープした形（`1\.7\.1` のような形）。describe の題名やコメントの中の言及（例: `'v1.7.1 T12: …'`、`例: 1.7.1.1`）は対象にしない |
| A8 | 受け入れ条件: `grep -rn "'1\.7\.1'" tests/` が許可リスト以外で 0 件 | 版の文字列の許可リストは空。現在 0 件（確認済み） |
| A9 | 受け入れ条件: 違反する一時ファイルを置くと落ちることを、テスト自身の中で確かめる | `os.tmpdir()` の下に一時ディレクトリを作り、`tests/` に違反を置いて検査関数が違反を返すことを確かめる（陽性）。違反の無いファイル・許可リストのファイル・スナップショットの場所に置いたものでは違反にならないこと（陰性）も確かめる。実際の `tests/` には一時ファイルを置かない（並行に走る他のテストが拾うおそれと、消し忘れを避けるため） |

解釈で決めたこと（指示書に無い・曖昧な点）:

- **「読む」の範囲**: ソースの静的な検査なので、src のモジュール（`matchOfflineAdvisories` など）を経由した間接的な利用は (1) では検出しない。間接的な利用は A4 の setupFiles で固定 DB に向ける。ただし `getAdvisoryDbMetadata()` は差し替えを見ずに常に同梱 DB を読むので、これを呼ぶテスト（advisory.test.ts の D17）は許可リストのファイル（advisory-db-invariants.test.ts）に移し、件数の下限の比較を同梱 DB の値との一致に変えた。
- **版の直書きの範囲**: 「現在の版」に限る（指示書どおり）。過去の版（`'1.7.0'`、`'1.6.6'` など）を履歴データやパイプラインの合成データとして書くのは対象外。固定 DB の dataVersion（`'20261031'`）を固定 DB の照合結果の期待値として書くテスト（export / ui-escaping / advisory）は、同梱 DB に依存しないので今回は変えない。
- **advisory-pipeline.test.mjs の `'1.7.1'`**: classify-release の「3 要素の版は手動」を確かめる合成データで、現在の版とたまたま同じ値だった。許可リストに入れると本当の直書きも見逃すので、`'1.7.2'` に変えた（判定は要素数だけで決まるので、期待値は変わらない）。
- **security.test.ts の `extensionVersion: '1.7.1'`**: レポートの入力データ。`readPackageVersion()` に変えた（期待値は変わらない）。
- **setup ファイルの置き場所**: setup ファイルはテストの一部なので、設計とテストの担当が `tests/setup/advisory-db.ts` に作った。実装の担当は vite.config.ts に 1 行足すだけにする。
- **各テストの前に差し替え直す**: 既存テストに `afterEach(() => setTestAdvisoryDatabase(null))` があるので、setup では読み込み時に加えて `beforeEach` でも固定 DB を入れ直す。null に戻すと同梱 DB になる src 側の挙動は変えない。

## 実装の方針

実装の担当が変えるのは **`vite.config.ts` だけ**（INSTRUCTIONS.md §2.1 で T01 の setupFiles として許可）。

```ts
/// <reference types="vitest" />
import { resolve } from 'node:path';
import { defineConfig } from 'vite';

export default defineConfig({
  build: { /* 既存のまま */ },
  test: {
    setupFiles: ['tests/setup/advisory-db.ts'],
  },
});
```

- `test.setupFiles` に文字列 `'tests/setup/advisory-db.ts'` をそのまま書く（テストは vite.config.ts のテキストに `setupFiles` と `tests/setup/advisory-db.ts`（`.ts` は省略可）が引用符で閉じて現れることを確かめる）。`resolve(__dirname, 'tests/setup/advisory-db.ts')` の形でもテキストに含まれるので可。
- vite.config.ts は tsconfig の include に入っていないので、型検査には影響しない。`/// <reference types="vitest" />` は編集時の型補完のためで、必須ではない。
- `build` の設定は変えない。他の test 設定（include、environment など）は足さない（既存のテストの集め方が変わるため）。

テストが前提にしている公開 API（すべて既存か、設計とテストの担当が tests/ に作成済み）:

| 場所 | 名前 | 型 | 作成 |
| --- | --- | --- | --- |
| `src/detection/advisory.ts` | `setTestAdvisoryDatabase(db: Partial<AdvisoryDatabase> \| null): void` | 既存 | 変更しない |
| `src/detection/advisory.ts` | `matchOfflineAdvisories(...)` の `advisoryDataVersion` / `productAdvisoryCount` | 既存 | 変更しない |
| `scripts/advisories/build-db.mjs` | `MIN_EXTENSION_VERSION` / `OUTPUT_SCHEMA_VERSION` | 既存の export | 変更しない（§2.3 で変更禁止） |
| `tests/helpers/release-version.ts` | `isSameRelease(manifestVersion: string, pkgVersion: string): boolean`、`readPackageVersion(): string`、`REPO_ROOT: string` | 新規 | 設計とテストの担当が作成済み |
| `tests/helpers/test-hygiene.ts` | `scanTestHygiene(options): HygieneViolation[]`、`findBundledAdvisoryDbReads`、`findVersionLiterals`、`listTestSourceFiles`、`BUNDLED_DB_READ_ALLOWLIST`、`VERSION_LITERAL_ALLOWLIST` | 新規 | 設計とテストの担当が作成済み |
| `tests/setup/advisory-db.ts` | 読み込み時と `beforeEach` で `setTestAdvisoryDatabase(固定 DB)` を呼ぶ | 新規 | 設計とテストの担当が作成済み |

確認済みのこと: `tests/setup/advisory-db.ts` を setupFiles に入れた状態（一時の設定ファイルで模擬）で、既存テストを含む全テストが合格した（vite.config.ts のテキストを見る 1 件だけは、実装の前なので不合格）。既存のテストで、同梱 DB の中身に暗黙に依存して落ちるものは無かった。

## 実装の担当への注意

- **`tests/` と設計メモは変更しない**。テストが仕様と合わないと考えたら `.agy-out/result.json` に `needsTestChange: true` と理由を書いて終える。
- 変えるのは `vite.config.ts` だけ。`src/detection/advisory.ts`（`setTestAdvisoryDatabase` の挙動、`getAdvisoryDbMetadata` が同梱 DB を読むこと）は変えない。null で同梱 DB に戻る挙動を変えると、既存テストの意味が変わる。
- `scripts/advisories/build-db.mjs`（`MIN_EXTENSION_VERSION` の出どころ）、`src/detection/advisory-db.json`、`data/advisories/` は変更禁止（§2.3）。
- `test.include` や `environment` を足さない。既定の include（`**/*.{test,spec}.?(c|m)[jt]s?(x)`）のままで `tests/advisory-pipeline.test.mjs` も集まっている。`tests/setup/` と `tests/helpers/` のファイルは名前に `.test.` が無いので、テストとしては集まらない。
- setupFiles のパスは root（リポジトリ直下）からの相対で解決される。
- 今後のタスクでテストを書くときは、現在の版を引用符で囲んで書かない（`readPackageVersion()` を使う）。T09 で package.json を 1.8.0 にすると、`'1.8.0'` が直書きの対象になる。
- 実行中のテストが標準エラーに出すスタックトレース（`at startTests …`）は、変更前から出ているもので、失敗ではない。
