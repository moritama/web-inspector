# T07 設計メモ — test-server の確認ページと HTTPS 専用ヘッダーの「対象外」

## 目的

HTTPS でしか効かないヘッダー（COOP・COEP）を、HTTP のページでは新しい status「対象外」（`not-applicable`）にし、要確認件数・内訳・バッジ・エクスポートの件数に数えない（H6）。あわせて、手動確認用のページ（WAF 確認画面、外部 CDN の SRI、ディストリのバナー、HTTPS 専用ヘッダー）を test-server に足し、サーバーを起動しない単体テストで各ページのヘッダーを確かめられる形にする。

## 仕様の解釈

指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **対象のヘッダー。** HTML の仕様で、COOP は「obtain an opener policy」、COEP は「obtain an embedder policy」の手順 2 が「安全でないコンテキスト（non-secure context）なら新しい（既定の）ポリシーを返す」。HTTP のページではブラウザがヘッダーを無視するので対象外にする。CORP（Fetch）と Permissions-Policy には secure context の要件が無いので対象にしない。Reporting-Endpoints（Reporting API）は secure context が条件だが、独立したチェックが無く、関係する `SEC-CSPX-REPORT-01` は CSP の `report-to` の名前の不一致を見るもので、HTTP でも設定の誤りとして意味があるため、今回は対象にしない（未解決に記録）。HSTS は既存のまま（HTTP のページでは `SEC-HSTS-` の項目を作らない今の動きを変えない）。
2. **HTTP のページで COOP の項目をいつ作るか。** HTTPS では「無い」「無効な値」のときに info を出していた。HTTP ではヘッダーがあってもなくても効かないので、**COOP は値にかかわらず `SEC-COOP-01` を対象外で 1 件**出す（有効な値でも「HTTP では効かない」ことが分かるようにする）。COEP は既定で推奨しない（v1.8.0 T06）ので、**ヘッダーがあるときだけ**対象外を 1 件出し、無いときは項目を作らない。どちらも warning ではないので警告は増えない。
3. **status の名前と表示。** 既存の `runtimeStatus` と網羅性（coverage）が `'not-applicable'` を使っているので、同じ綴りを `SecurityStatus` に足す。ポップアップとダッシュボードのラベルは「対象外」。プレーン表記と Markdown の表記は `N/A`（ほかの表記と同じく英字の短い記号。太字にしない）。テストは「ほかの status と区別でき、太字でない」ことと、`getSecurityCheckDisplayBadge` の `statusCode`・`markdownBadge` が `formatPlainStatusCode`・`formatMarkdownStatusBadge` と一致することだけを見る（`N/A` の字面はテストしない）。
4. **件数の扱い。** 対象外は、要確認件数・CRITICAL〜LOW・INFO・UNKNOWN のどれにも入れない。代わりに `securityFindings.notApplicable`（任意の項目）に数える。INFO に入れないのは、「参考情報・問題のない項目」と性質が違い、HTTPS に移したときの差分（Resolved / Regressed）にも影響しないため。バッジ（`updateBadge`）は要確認件数で決まるので、対象外は入らない。
5. **未観測との優先順位。** 既存の SPEC-01 の処理（`executeInspection` でヘッダー未観測のとき、`HEADER_DEPENDENT_CHECK_PREFIXES` の項目の status を unknown に上書き）が、対象外より後に動くので、未観測なら unknown になる。この順番を変えない。
6. **test-server の形。** サーバーを起動しない単体テストにするため、`server.mjs` をリクエストハンドラーと起動の入口に分ける。import しただけでは listen せず、`node test-server/server.mjs`（`npm run test-server`）で実行したときだけ起動する。ページの一覧は `TEST_PAGES` 1 か所にまとめ、起動時の表示はそこから作る。
7. **ディストリのバナーの版の選び方。** 「版の文字列は distro-map.json から取る」を、ハンドラーが対応表を読み、下の「実装の方針」の規則で版とリリースを選ぶ、と解釈した。パッケージ版の revision の部分（`-1ubuntu0.1`、`-1~debNu1` など）は版の書式の例で、上流の版ではないので固定の形を使ってよい（Debian の N と Ubuntu の YY.MM はリリースから取る）。対応表に無い版は、対応表の版から作る（直接書かない）。
8. **WAF のページの HTTP の状態コード。** AWS の文書では CAPTCHA は 405、Challenge は 202、Cloudflare の確認画面は 403 で返る。手動確認の再現のため、その状態コードを返す（テストは 500 未満であることだけを見る）。

## 実装の方針

### 1. 「対象外」の status（src/shared/types.ts）

- `SecurityStatus` に `'not-applicable'` を足す: `export type SecurityStatus = 'pass' | 'warning' | 'fail' | 'info' | 'unknown' | 'not-applicable';`
- `InspectionReport['summary']['securityFindings']` に任意の項目 `notApplicable?: number;`（対象外の件数）を足す。過去の履歴データには無いので任意にする。

### 2. 件数と表示（src/shared/security-status.ts）

- `isRequiresAttention`: 変えない（warning / fail だけなので対象外は false のまま）。
- `summarizeSecurityChecks`: status が `'not-applicable'` の項目を数え、`securityFindings.notApplicable` に入れる（常に数値で返す。0 でもよい）。INFO（pass / info）と UNKNOWN には入れない。CRITICAL〜LOW は今のまま要確認の項目だけ。
- `formatPlainStatusCode('not-applicable')` → `'N/A'`。`formatMarkdownStatusBadge('not-applicable')` → `'N/A'`（太字にしない）。
- `getSecurityCheckDisplayBadge`: status が `'not-applicable'` のときは severity にかかわらず `{ badgeClass: 'sev-not-applicable', dashLabel: '対象外', popupLabel: '対象外', statusCode, markdownBadge }` を返す（`unknown` と同じく早めに返す）。
- CSS: `src/popup/popup.css` と `src/dashboard/dashboard.css` に `.sev-not-applicable` を足す（見た目は `.sev-unknown` と同じでよい）。

### 3. COOP・COEP（src/security/headers.ts の `checkHttpHeaders`）

- COOP（今の「7.5 Cross-Origin 系ヘッダー」の COOP の部分）: `isHttps` が false なら、値にかかわらず次の 1 件だけを出し、今の判定（info）は行わない。`isHttps` が true のときは今のまま。

  ```ts
  {
    checkId: 'SEC-COOP-01',
    category: 'http-headers',
    name: 'Cross-Origin-Opener-Policy (COOP)',   // 今と同じ名前（R05: 同じ項目名で status を変えても名前は変えない）
    status: 'not-applicable',
    severity: 'info',
    observed: coop ?? 'ヘッダー未設定',            // 値があればそのまま入れる
    description: '…HTTPS のページでだけ有効で、HTTP のページではブラウザがこのヘッダーを無視するため、評価の対象外です。',  // 「HTTPS」を含める
    recommendation: '…HTTPS で配信したうえで、COOP の設定を確認してください。',
    referenceUrls: [MDN の COOP の URL（今と同じ）, 'https://html.spec.whatwg.org/multipage/browsers.html#the-coop-headers'],
    scope: url,
  }
  ```

- COEP: ヘッダーがあるときだけ。`isHttps` が false なら値にかかわらず `SEC-COEP-01`（name は今と同じ `'Cross-Origin-Embedder-Policy (COEP)'`、status `'not-applicable'`、severity `'info'`、observed は値、description に「HTTPS」を含め HTTP では無視されることを書く、referenceUrls に MDN の COEP と `https://html.spec.whatwg.org/multipage/browsers.html#the-coep-headers`）を 1 件。`isHttps` が true のときは今のまま。ヘッダーが無いときは HTTP でも HTTPS でも項目なし。
- CORP・X-XSS-Protection・ほかのチェックは変えない。HSTS も変えない。
- `HEADER_DEPENDENT_CHECK_PREFIXES`（src/background/service-worker.ts）は変えない（`SEC-COOP-`・`SEC-COEP-` は既にある）。未観測のときの unknown への上書き（SPEC-01）も変えない。

### 4. エクスポートと整合性チェッカー

- Markdown（src/export/markdown.ts）: 表は既に `formatMarkdownStatusBadge` を使うので、そのままで `N/A` になる。ロードマップは `isRequiresAttention` で選ぶので対象外は載らない。追加の変更は不要（概要の表に対象外の行を足す必要はない）。
- JSON・CSV: status をそのまま出すので変更不要。
- `scripts/report-lint.mjs` の `expectedMarkdownStatusBadge` に `case 'not-applicable': return 'N/A';` を足す（足さないと既定の `NOT-APPLICABLE` と比べて R02 が落ちる）。R01 の INFO・UNKNOWN の数え方（pass / info、unknown）は今のままで、対象外を数えない `summarizeSecurityChecks` と一致する。
- `docs/DETECTION_SPECIFICATION.md`: セキュリティ診断の status の説明に `not-applicable`（対象外。HTTP のページの COOP・COEP。件数に数えない。未観測なら unknown が優先）を足す。

### 5. test-server（test-server/server.mjs）

テストが前提にする公開 API（ES モジュールの名前付き export）:

```js
/** 起動時の一覧に載せるページ（既存の表示していたページ ＋ 新しいページ） */
export const TEST_PAGES; // ReadonlyArray<{ path: string; label: string }>

/** 起動時に console.log する行。TEST_PAGES の全ページについて `http://localhost:${port}${path}` を含む行を返す */
export function getStartupLines(port); // (port: number) => string[]

/** リクエストハンドラーを作る。options.distroMap を省略すると data/advisories/distro-map.json を読む */
export function createRequestHandler(options); // (options?: { distroMap?: { entries: DistroMapEntry[] } }) => (req, res) => void
```

- 今の `http.createServer((req, res) => { … })` の中身を `createRequestHandler` が返す関数に移す。既存のページの動き（パス・ヘッダー・本文）は変えない。
- 起動は、このファイルを直接実行したときだけにする。例:

  ```js
  const isMain = (() => {
    try {
      return Boolean(process.argv[1]) && fs.realpathSync(process.argv[1]) === fs.realpathSync(fileURLToPath(import.meta.url));
    } catch {
      return false;
    }
  })();
  if (isMain) {
    http.createServer(createRequestHandler()).listen(PORT, () => {
      for (const line of getStartupLines(PORT)) console.log(line);
    });
  }
  ```

- ハンドラーが使う `req` は `req.url`・`req.headers.host` だけ、`res` は `statusCode`・`setHeader`・`getHeader`・`hasHeader`・`removeHeader`・`writeHead(code[, headers])`・`write`・`end` だけにする（テストの偽の res がこれだけを持つ）。
- `TEST_PAGES` には、今 `server.listen` のコールバックで表示している 11 ページ（`/`・`/insecure-cookie`・`/loose-csp`・`/legacy-lib`・`/edge-cases`・`/rails-session`・`/react18-app`・`/vue3-app`・`/bootstrap-only`・`/distro-apache`・`/spa-settle`）と、下の新しい 10 ページを入れる。ラベルは日本語。`getStartupLines` の 1 行目は今と同じ「`[test-server] テストサーバーが起動しました: http://localhost:<port>`」でよい。各ページの行は `  - <label>: http://localhost:<port><path>` の形。
- 新しいページはどれも `Content-Type: text/html; charset=UTF-8` で、既存の `createLayout` を使い、本文（h1 など）に自分のパスを書く（例 `(/sri-cdn)`）。本文に「期待される結果」を書く。対応表から作った値を本文に出すときは HTML エスケープする。ナビゲーション（`createLayout` の nav）に足すかは任意。

ディストリのバナーの値の選び方（`map` は `createRequestHandler` に渡された対応表、または読み込んだ `distro-map.json`。`entries` のファイルの順で探す）:

- **U（Ubuntu）**: `family === 'ubuntu'` のリリースのうち、`product === 'apache'` と `product === 'php'` の両方の項目があるもので、`entries` の中で最初に出てくるリリース。`Ua` = その apache の項目の `upstreamVersions[0]`、`Up` = php の項目の `upstreamVersions[0]`、`UN` = `release` の `:` の後ろ（例 `ubuntu:18.04` → `18.04`）。
- **D（Debian）**: 同じ規則で `family === 'debian'`。`Da`・`Dp`、`DN` = `release` の `:` の後ろ（例 `debian:10` → `10`）。
- **R（RHEL）**: `family === 'rhel'` かつ `product === 'apache'` の最初の項目の `upstreamVersions[0]`。
- **X（対応表に無い版）**: `Ua` を `.` で分け、最後の数字の部分に 1 を足すことを、`family === 'ubuntu'` かつ `product === 'apache'` のどの項目の `upstreamVersions` にも無くなるまで繰り返した版。
- 選べないとき（対応表が読めない、該当の項目が無い）は、そのページは 200 で説明だけを返し、バナーのヘッダーを付けない（サーバーを止めない）。
- 同梱の対応表では、たとえば U は Ubuntu 18.04、D は Debian 10 になるが、**版やリリースの文字列をコードに書かない**（テストは合成の対応表を渡して、版が対応表から来ていることを確かめる）。

## 実装の担当への注意

- **`tests/` と設計メモは変更しない。** テストが仕様と合わないと考えたら `.agy-out/result.json` に `needsTestChange: true` と理由を書く。
- **未観測の上書き（SPEC-01）の順番を変えない。** 対象外は `checkHttpHeaders` で作り、`executeInspection` の「ヘッダー未観測なら unknown」がその後で上書きする。`HEADER_DEPENDENT_CHECK_PREFIXES` から `SEC-COOP-`・`SEC-COEP-` を外さない。
- **HTTPS の結果を変えない。** COOP・COEP の HTTPS の分岐（info の条件・文言）は今のまま。ほかのチェック（CORP・X-XSS・HSTS など）は HTTP でも変えない。
- **項目名を変えない。** 対象外の項目の `name` は HTTPS のときと同じにする（整合性チェッカーの R05 が、同じ項目名の status による揺れを見る）。
- **文言に「安全」「該当なし」を使わない。** 総合チェック C18 が `src/` の文言を検索する。secure context は「HTTPS のページ」「secure context（HTTPS）」と書き、「安全なコンテキスト」と訳さない。
- **`formatPlainStatusCode`・`formatMarkdownStatusBadge` は switch で全 status を返す**。新しい case を足さないと型検査で「戻り値の無い経路」になる。
- **test-server を import しただけで listen しない。** 起動の判定は `fs.realpathSync` で両方のパスを解決してから比べる（macOS の `/tmp` などシンボリックリンクの差で入口が動かなくならないように）。`npm run test-server` で今までどおり起動し、一覧が表示されること。
- **ディストリのバナーの版・リリースの文字列をコードに書かない。** 対応表から「実装の方針 5」の規則で選ぶ。`createRequestHandler({ distroMap })` に渡された対応表を必ず使い、渡されなければ `distro-map.json` を読む（テストは合成の対応表を渡す）。`data/advisories/distro-map.json` は T07 では変更しない（K2.2）。
- **既存のページの動きを変えない。** 既存のパス・ヘッダー・本文はそのまま `createRequestHandler` に移す。既定のページ（どのパスにも当たらないとき）も今のまま。
- **拡張に外部への通信を足さない。** SRI のページの CDN の URL は test-server が返す HTML の中だけ（拡張のコードには入れない）。
- 新しい依存パッケージは足さない。指示に無いリファクタリングはしない（test-server の分割は受け入れ条件「起動しない単体テスト」のため）。
