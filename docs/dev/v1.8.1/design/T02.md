# T02 設計メモ — OS のライフサイクル表と対応表、DB への組み込み

## 目的

第2段階（T03 の OS リリースの推定と EOL 判定）と第3段階（T05・T06）の土台として、OS のライフサイクル（endoflife.date）と、上流版→OS リリースの対応表（curated の `distro-map.json`）を、DB パイプライン（fetch-upstream → build-db → DB だけのリリース）に載せる。advisory-db.json に `distro` 節（`releases`・`map`）を足し、schema を 2.3 にする（H7）。

## 仕様の解釈

受け入れ条件と指示書の本文を、テストで確かめられる形に言い直す。

| # | 指示書 | テストで確かめる形 |

| B5 | OS のライフサイクルの取得結果が無いとき、build-db は警告を出して `distro.releases` を空にし、失敗しない | 取得結果が無い → 例外なし、`releases` は `[]`、`report.distro.warnings` が空でない、`map` は出る。一部の系統だけ無い → ある系統だけ出し、無い系統の名前を警告に書く |
| B6 | 固定 DB に `distro` 節を足すのは設計の担当 | 固定 DB を schema 2.3 にし、`distro` 節（releases 7 件・map 19 件の抜粋）と `integrity.distroDigest` を足した（設計の担当が実施済み） |

指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **「標準サポート終了」と「延長サポート終了」の対応（§5.1）。** endoflife.date の `eol` を `standardSupportEnd`、`extendedSupport` を `extendedSupportEnd` にする。Ubuntu の `eol` は標準サポートの終了、`extendedSupport` は ESM（Ubuntu Pro）の終了。Debian の `eol` は Debian LTS を含む終了日、`extendedSupport` は ELTS。RHEL の `eol` はメンテナンスの終了、`extendedSupport` は ELS。H4 の文言「標準サポート終了（ESM / ELS で延長されている可能性あり）」と合う。`extendedSupport` が `false`・無い（CentOS・AlmaLinux・Rocky）ときは `null`。`eol` が日付でない（`true`/`false`）ときも `null`（対象のリリースはすべて日付があることを確かめた）。endoflife.date の `support`（アクティブサポートの終了）は使わない（取得結果には保存する）。
2. **`lts`。** endoflife.date の `lts` は Ubuntu では真偽値、RHEL では日付の文字列。`true` または文字列なら `true`、それ以外は `false`。
3. **H8 の「その時点でサポート中の中間リリース」。** 2026-11-14 時点で Launchpad の `supported: true` の中間リリースは 26.10（stonking）だけ（25.10・25.04 は Obsolete、27.04 は開発中）。26.04 LTS（resolute）は H8 の一覧に無いが、サポート中の LTS なので収録する（推定の候補から最新の LTS が抜けるほうが誤判定につながる）。
4. **RHEL 系の対応表（H1 により第2段階まで）。** RHEL 本体のパッケージ一覧はログインが要るため、ソースが同じ再ビルド（Rocky Linux・AlmaLinux・CentOS の公開リポジトリ）で確かめた。RHEL と Rocky は同じ上流版。確かめられなかった製品（RHEL 7 / CentOS 7 の openssl・php、RHEL 8 系の php、AlmaLinux 8・9 の一部など）は**載せない**。載っていない版は T03 で確信度 none（第1段階の表示のまま）になり、誤った推定より安全。
5. **upstreamVersions に何を載せるか。** 各リリースで（Release・Updates・Security のポケット、Debian では安定版とセキュリティ更新・LTS の更新で）配布された上流版。Debian の revision・epoch・`~` の付いた版は載せない（上流版だけ）。Ubuntu の開発中だけにあった版（Proposed・リリース前の版）は載せない。
6. **evidenceUrl のホスト。** 指示書は「一次資料」とだけ書いている。誤って二次情報のサイトを書かないよう、build-db と validateDb で許可するホストを、ディストリ自身の公開サイトに限る（下の「実装の方針」の一覧）。
7. **対応表の不正（curated の誤り）は build-db を失敗させる。** 人が編集する curated なので、黙って捨てずに止める（`distro-map.json` が無いときだけは、空の対応表として扱い警告する）。一方、OS のライフサイクルの取得結果が無いのは外部の状態なので、指示書どおり警告だけにする。
8. **integrity の持ち方。** 既存の `integrity.digest`（libraries の sha256。拡張と既存のテストが前提にしている）は変えず、`integrity.distroDigest` を足す。`distro` 節があり integrity があるのに `distroDigest` が無い・一致しない DB は、validateDb が「integrity」を含むメッセージで拒否する（distroDigest を消して改ざんを隠せない）。
9. **`--distro-only` と manifest。** `--distro-only` の取得は、manifest の `fetchedAt`（build-db の基準日＝dataVersion になる）を前回のまま保つ。OS のライフサイクルを足しただけで DB 全体の日付が進むと、既存の製品のデータが新しく見えてしまうため（「既存の製品の取得結果は変えない」の解釈）。前回の manifest が無いときだけ今の日時。
10. **通常の取得でも OS を取る。** 週次の自動更新（`--distro-only` を付けない）でも OS のライフサイクルを取り、古くならないようにする。`--only` を付けたときは、従来の製品だけを取る（OS は取らない）。
11. **`distro` 節を出す条件。** `catalog.distros` があるか、`distroMap` が渡されたときだけ出す。どちらも無いとき（既存のテストの合成 catalog）は、`distro` 節も `distroDigest` も出さない（既存の出力の形を保つ）。schema はどちらでも 2.3。
12. **T05 で足すもの。** `distro.advisories` と `distro._source`（§5.2）は T05 の範囲。T02 では作らない。validateDb も T02 では `_source` を必須にしない（T05 で必須にする）。

```js

export const DISTRO_PRODUCTS = ['apache', 'nginx', 'php', 'openssl'];
/** evidenceUrl に許可するホスト（完全一致） */
export const DISTRO_EVIDENCE_HOSTS = new Set([
  'launchpad.net', 'api.launchpad.net',

export function validateDistroMapEntry(entry, releasesByFamily)  // 不正なら Error を投げる
export function buildDistroSection({ distros, distroEol, distroMap }) // => { distro: { releases, map }, warnings: string[] }
export function validateDistroSection(distro)             // validateDb から呼ぶ。不正なら Error
```

`validateDistroMapEntry` の規則（どれか 1 つでも外れたら Error）:

| 項目 | 規則 |
| --- | --- |
| `family` | `DISTRO_FAMILIES` のどれか |
| `release` | `/^([a-z]+):([0-9][0-9.]*)$/` で、前半が `family` と一致。`releasesByFamily` が渡されたときは後半がその系統の catalog の `releases` にある |
| `codename` | `null` または `[<>"'`]` と制御文字を含まない文字列 |
| `product` | `DISTRO_PRODUCTS` のどれか |
| `upstreamVersions` | 空でない配列で、各要素が `/^\d+(?:\.\d+)+[a-z]?$/`（例 `1.18.0`・`1.1.1f`。`1.18.0-6ubuntu14` は不可） |
| `sourcePackage` | `/^[a-z0-9][a-z0-9.+-]+$/` |
| `verifiedAt` | 実在する日付の `YYYY-MM-DD` |
| `evidenceUrl` | `isDistroEvidenceUrl` が真 |

`buildDistroSection` の出力:

- `map`: `distroMap.entries` の順に、各項目を検査し、次の 8 項目だけをこの順で持つオブジェクトにする: `family, release, codename, product, upstreamVersions, sourcePackage, verifiedAt, evidenceUrl`。同じ `release|product|sourcePackage` が 2 つあれば Error。`distroMap` が null / undefined なら `map: []` と警告。
- `releases`: catalog の `distros` の順、各系統の `releases` の順に、`distroEol[<slug>]` の `cycles` から `cycle` が一致するものを探して次の形にする（キーはこの順）:

```js
{ release: `${family}:${cycle}`, family, cycle,
  codename: cleanText(c.codename, 60) || null,   // HTML の特殊文字は全角に置き換わる
  lts: c.lts === true || typeof c.lts === 'string',
  releaseDate: 'YYYY-MM-DD' | null,
  standardSupportEnd: c.eol が日付の文字列ならその値、それ以外は null,
  extendedSupportEnd: c.extendedSupport が日付の文字列ならその値、それ以外は null }
```

- 系統の取得結果が無い → その系統は出さず、警告（系統のキーと slug を含む文。例「OS のライフサイクルの取得結果がありません: debian (debian)」）。サイクルが取得結果に無い → 警告（`family:cycle` を含む）。catalog に無いサイクルは出さない。

`validateDistroSection(distro)`: `distro` がオブジェクトで、`releases` と `map` が配列。`releases` の各要素は `release === family + ':' + cycle`、`family` が一覧にあり、`codename` が null か安全な文字列、日付の 3 項目が null か `YYYY-MM-DD`。`map` の各要素は `validateDistroMapEntry(e, null)`。

### 6. `scripts/advisories/build-db.mjs`

- `export const OUTPUT_SCHEMA_VERSION = '2.3';`（`MIN_EXTENSION_VERSION` は変えない。旧い拡張は `distro` 節を無視するだけで動くため）

### 7. `scripts/advisories/fetch-upstream.mjs`

- `parseArgs` を **export** し、`--distro-only` を `distroOnly: true` にする（既定 `false`）。既存の項目（`only`・`skipNvd`・`nvdRefreshDays`）はそのまま
- `catalog.distros` の各系統について `eolApiUrl(slug)` を `fetchJson` で取り、`compactDistroEolCycles` で圧縮して `<upstreamDir>/distro-eol/<safeFileKey(slug)>.json` に `{ slug, fetchedAt, cycles }` を書く。manifest のキーは `distro-eol:<slug>`（成功 `{ status: 'ok', count, fetchedAt }`、失敗は既存の `record` と同じく `stale`/`failed`）。既存の `record` を使えばよい
- `args.distroOnly` のとき: 製品（OSV・NVD・製品の EOL）・KEV・NVD スコア・PSL を**取らない**。OS だけ取る。manifest は `{ schemaVersion: 1, fetchedAt: <前回の fetchedAt。無ければ今>, sources: <前回の sources に distro-eol:* を上書きで足し、キーで並べたもの> }`。戻り値 `{ okCount, failCount, manifest }` の数は OS の分だけ
- `args.distroOnly` でなく `args.only` も無いとき（通常の週次の取得）: 従来の取得に加えて OS も取る
- `main()`: `--distro-only` のときは `includePsl` を false にする

### 8. `scripts/validate-advisories.mjs`

- `SUPPORTED_SCHEMA_VERSIONS` に `'2.3'` を足す
- 2.2 だけに掛けている厳格な検査（`origin`・`fixStatus`・`eol.eolDate` の書式）を 2.3 にも掛ける（`schemaVersion === '2.2'` を「2.2 または 2.3」に）
- `db.distro !== undefined` のとき `validateDistroSection(db.distro)` を呼ぶ（`lib/distro.mjs` を import してよい）
- `db.integrity` があり `db.distro !== undefined` のとき、`db.integrity.distroDigest !== sha256(JSON.stringify(db.distro))` なら Error（メッセージに `integrity` を含める。例「integrity.distroDigest が distro の内容と一致しません」）。`distroDigest` が無い場合も同じく Error

### 9. `scripts/ci/rehearse-db-release.mjs`

`bumpAdvisoryDb(db)`: 従来の処理に加え、`cloned.distro !== undefined` なら `cloned.integrity.distroDigest = sha256(JSON.stringify(cloned.distro))`。`distro` が無ければ `distroDigest` を付けない。`distro` 節の中身は変えない。

## 実装の担当への注意

- **`advisory-db.json` と `build-report.json` を手で作らない・直さない。** 実装の後にスクリプトが build-db を実行して作る。`tests/advisory-db-invariants.test.ts` の追記（同梱 DB の `distro` 節）は、その生成の後に通る。
- **`data/advisories/upstream/` に何も置かない。** OS のライフサイクルの取得はスクリプトが行う（H10）。取得前の同梱 DB は `distro.releases` が空で正しい。
- **既存の製品の出力を変えない。** `compactEolCycles`・`normalizeEol`・`libraries`・`coverage`・`integrity.digest`・`sources` はそのまま。OS を `catalog.products` に入れない（入れると libraries に OS が製品として現れ、C13 に反する）。
- **`--distro-only` で manifest の `fetchedAt` を進めない**（build-db の基準日が進み、dataVersion が変わってしまう）。
- `fetch-upstream.mjs` の `parseArgs` は今は export されていない。export する。
- validateDb の「2.2 だけに掛けている検査」を 2.3 にも掛けるのを忘れない（テストあり）。
- `bumpAdvisoryDb` は `rehearseDbRelease` の中でも使われる。`distro` 節があるときに `distroDigest` を付け直さないと、予行で integrity の検査が落ちる。
- 対応表と catalog の値は、この設計メモの JSON をそのまま写す。表に無い版・リリースを足さない（K6）。RHEL 系で載っていない製品は、確かめられなかったため意図して載せていない。
- `distro.advisories` と `distro._source` は T05 で足す。T02 では作らない。
- テストは `tests/fixtures/advisory-upstream.mjs` の合成の上流データ（`fetchedAt` が過去の日付）を使う。build-db の `generatedAt` の検査（未来を拒否）に引っかからない。
