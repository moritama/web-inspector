# T06 設計メモ: 同梱データの出典（データと生成、E）

## 目的

advisory-db.json の `sources`（今は文字列の配列）を、`distro._source` と同じ形のオブジェクトの配列（name・url・ecosystem・license または licenseNote・retrievedAt・recordCount）にして、スキーマを 2.4 に上げる（H10・§5.3）。すべての出典に license か licenseNote を持たせ（H9・§5.2）、CI で確かめる。古いスキーマ（文字列の配列）の DB を読む側は壊さない。PSL の生成ファイル `src/security/psl-rules.generated.ts` の先頭に MPL 2.0 の表示と元のファイルの URL を出す。

## 仕様の解釈

受け入れ条件（指示書 §6 T06）と §5.2・§5.3 を、テストで確かめられる形に言い直す。

1. **すべての出典に license か licenseNote**
   - build-db の出力の `sources` の全要素で `license`（空でない文字列）か `licenseNote`（空でない文字列）の少なくとも一方がある。`license` のキーは常にあり、値は文字列か `null`。
   - `validateDb`（scripts/validate-advisories.mjs）が、schema 2.4 の DB でこれを満たさない要素を拒否する。
   - CI のチェック `scripts/ci/check-data-sources.mjs` が、同梱 DB の `sources` と `distro._source` の全要素でこれを確かめ、満たさなければ不合格にする。
2. **スキーマ 2.4**
   - `OUTPUT_SCHEMA_VERSION` が `'2.4'`。生成した DB と、夜のシェルが build-db し直した同梱 DB の `schemaVersion` が `'2.4'`。
   - `sources` に文字列の要素が無い。各要素は `distro._source` と同じ形（`ecosystem` も持つ。Debian・Ubuntu はその名前、他は `null`）。
3. **古いスキーマを読む側が壊れない**
   - `validateDb` は schema 2.1〜2.3 で `sources` が文字列の配列の DB をこれまでどおり受け付ける。
   - 拡張機能の側（`src/detection/advisory.ts`）は、文字列の配列・オブジェクトの配列・混在のどれでも例外を投げない。`getAdvisoryDbMetadata().sources` は従来どおり `string[]`（出典の名前）で、構造化した出典は新しい任意の項目 `sourceRecords` に入れる。照合（`matchOfflineAdvisories`）の結果は `sources` の形に依存しない。
   - 古い文字列からは、ライセンス・URL・件数・日時を**作らない**（`null`）。推測で埋めない（K3・安全側）。
4. **サイズの上限内**: 同梱 DB のファイルサイズが `SIZE_LIMITS.advisoryDb`（check-size）以下、distro 節が `SIZE_LIMITS.distro` 以下。出典は数百バイト増えるだけなので、実装で特別な対処は要らない。
5. **PSL の生成ファイルの先頭に MPL 2.0**: `renderPslGeneratedTs` の出力で、最初の `export` より前（先頭のコメントの中）に「Mozilla Public License」「2.0」「https://mozilla.org/MPL/2.0/」と元のファイルの URL（`PSL_UPSTREAM_URL` = `https://publicsuffix.org/list/public_suffix_list.dat`）がある。リポジトリの `src/security/psl-rules.generated.ts` も先頭 2,000 文字以内にある（総合チェック C22 と同じ範囲）。

### 解釈したこと（指示書が曖昧な点）

- **どの出典を `sources` に載せるか**: §5.2 の表のうち、advisory-db.json に入るデータの 6 つ（NVD・GitHub Advisory Database・Ubuntu・Debian・endoflife.date・CISA KEV）。Ubuntu と Debian は distro 節があるときだけ（今の生成と同じ条件）。PSL は DB に入らない（別の生成ファイル）ので載せない。Launchpad・sources.debian.org・curated.json は「表示不要」（§5.2 の表の下）なので載せない。今の文字列の `'Curated (data/advisories/curated.json)'` は外す（自作のデータで、出典の表示の対象ではないため。curated の由来は `coverage.byProduct[*].sources` に残る）。
- **出典の定義をどこに置くか**: `data/advisories/catalog.json` は変更禁止（K2.3）なので、出典の名前・URL・ライセンスは `scripts/advisories/lib/sources.mjs`（新規。T06 の implAllow の範囲）に定数で持つ。catalog.json の `distroSources` の Debian の `licenseNote` は仮の値（「v1.8.2 で確認」）のままで、`distro._source` もそのまま（下の「未解決」）。最上位の `sources` の Debian は §5.3 の指定どおり `licenseNote: "ライセンスの明記なし（出典のみ表示）"`。
- **retrievedAt と recordCount の意味**: `distro._source` と同じく「その出典のスナップショットの取得日時（いちばん新しいもの）」「その出典に由来して DB に入った件数」。スナップショットが無ければ `null` と `0`（日時や件数を作らない）。定義は下の「実装の方針」の表のとおり。
- **CI の NOTICES の照合**: §5.3 の「THIRD_PARTY_NOTICES.md に DB の出典がすべて載っている」は、NOTICES を作るのが T07 なので、T06 のチェックは「ファイルがあれば照合し、無ければ警告だけ（合格）」にする。T07 にはチェック（scripts/ci/）を変える権限が無いため、照合の仕組みは T06 で入れておく。ファイルが無いこと自体は総合チェック C22 が不合格にする。照合は名前か URL のどちらかが本文にあれば載っているとみなす（C22 と同じ基準。表記の揺れで落とさない）。
- **NVD の表示文の一字一句**: 指示書 §5.2 は「This product uses the NVD API but is not endorsed or certified by the NVD.」と書くが、NVD のページは JavaScript で描画されるため本文を取得できず、逐語では確かめられなかった（検索の要約では「This product uses data from the NVD API but is not endorsed or certified by the NVD.」という表記もある）。表示文を画面に出すのは T07 なので、T06 の DB の licenseNote には英文を入れず、日本語で趣旨だけを書く（下の JSON）。T07 で一次資料を確かめる（未解決）。

## 実装の方針

### 1. `scripts/advisories/lib/sources.mjs`（新規）

出典の定義と、最上位の `sources` を組み立てる純粋関数を置く（名前はテストが前提にしていない。build-db から呼ぶ）。

```js
/** 最上位の sources の定義（§5.2。値は下の JSON をそのまま使う） */
export const DB_SOURCE_DEFINITIONS = [ /* 下の JSON の 6 要素（key は内部用。出力に含めない） */ ];

/**
 * @param {{ upstream: object, libraries: object, eolSourceByProduct: Record<string,string>, distroSection: object|null }} input
 * @returns {Array<{name,url,ecosystem,license,licenseNote?,retrievedAt,recordCount}>}
 */
export function buildDbSources(input) { ... }
```

出力の各要素は `distro._source` と同じ項目の順（`name`・`url`・`ecosystem`・`license`・`licenseNote`（あるときだけ）・`retrievedAt`・`recordCount`）。出力の順番は定義の順（NVD → GitHub Advisory Database → Ubuntu → Debian → endoflife.date → CISA KEV）。distro 節が無いときは Ubuntu と Debian を出さない。

定義（`key` は内部で使うだけで出力しない。出力にはそれ以外の項目をそのまま写す）:

```json
[
  { "key": "nvd", "name": "NIST National Vulnerability Database (NVD)", "url": "https://nvd.nist.gov/", "ecosystem": null, "license": null, "licenseNote": "米国政府（NIST）の公開データ。NVD API の利用規約に従い、NVD の表示文を拡張機能内に載せます（NVD による承認・認定は受けていません）" },
  { "key": "ghsa", "name": "GitHub Advisory Database (OSV.dev 経由: npm / Packagist)", "url": "https://github.com/github/advisory-database", "ecosystem": null, "license": "CC-BY-4.0", "licenseNote": "OSV.dev 経由で取得し、影響範囲・重大度・タイトルを加工して収録しています" },
  { "key": "ubuntu", "name": "OSV.dev (Ubuntu Security Notices)", "url": "https://github.com/canonical/ubuntu-security-notices", "ecosystem": "Ubuntu", "license": "CC-BY-SA-4.0", "licenseNote": "Ubuntu の部分は CC BY-SA 4.0 です。OSV.dev 経由で取得し、状態・修正版を加工して収録しています" },
  { "key": "debian", "name": "OSV.dev (Debian Security Tracker)", "url": "https://osv.dev/list?ecosystem=Debian", "ecosystem": "Debian", "license": null, "licenseNote": "ライセンスの明記なし（出典のみ表示）" },
```

- 文字列に `< > " ' \``・制御文字を入れない（validateDb の UNSAFE_TEXT）。上の値はそのまま使ってよい。
- Ubuntu・Debian・endoflife.date の `name`・`url` は catalog.json の `distroSources` と同じにしてある（NOTICES と画面の表記をそろえるため）。

retrievedAt と recordCount（`v` は `libraries[*].versions[*]`）:

| key | retrievedAt（いちばん新しいもの。無ければ null） | recordCount |
| --- | --- | --- |
| nvd | `upstream.nvd[*].fetchedAt`・`upstream.nvdScores[*].fetchedAt`・`upstream.manifest.sources` のキーが `nvd:` で始まるか `nvd-scores` の要素の `fetchedAt` | `v.sources` に `'nvd'` を含む件数 |
| ghsa | `upstream.osv[*].fetchedAt`・manifest のキーが `osv:` で始まる要素の `fetchedAt` | `v.sources` に `'osv'` を含む件数 |
| ubuntu / debian | `distro._source` の同じ `ecosystem` の要素の値をそのまま写す | 同左 |
| endoflife | `upstream.eol[*].fetchedAt`・`upstream.distroEol[*].fetchedAt`・manifest のキーが `eol:` か `distro-eol:` で始まる要素の `fetchedAt` | `report.products[k].eolSource === 'endoflife.date'` の製品の `libraries[k].eol.length` の和 ＋（distro 節があれば）`distro._source` の `ecosystem: null` の要素の `recordCount` |
| kev | `upstream.manifest.sources.kev.fetchedAt`（`upstream.kev.fetchedAt` があればそれも候補） | `v.kev === true` の件数 |

- 「いちばん新しい」は ISO 8601 の文字列の比較でよい（既存の `buildDistroSources` と同じ）。`fetchedAt` が文字列でない要素は無視する。
- 上流のスナップショットが 1 つも無ければ、どの出典も `retrievedAt: null`・`recordCount: 0`（要素自体は出す）。

### 2. `scripts/advisories/build-db.mjs`

- `OUTPUT_SCHEMA_VERSION = '2.4'`。冒頭のコメントのスキーマの説明も 2.4（sources の構造化）に直す。
- `db.sources` を `buildDbSources({ upstream, libraries, eolSourceByProduct, distroSection })` の戻り値にする。`eolSourceByProduct` は `report.products[k].eolSource`。
- `MIN_EXTENSION_VERSION` は変えない（総合チェック C13 が変更を不合格にする。拡張機能の側は下の 6 で新旧どちらも読めるようにする）。
- `libraries`・`distro`（releases・map・advisories・_source）・`integrity` の計算は変えない（C13: 脆弱性の中身が起点から変わらない）。

### 3. `scripts/validate-advisories.mjs`（`validateDb`）

- `SUPPORTED_SCHEMA_VERSIONS` に `'2.4'` を足す。`schemaVersion === '2.2' || '2.3'` で行っている厳格な検査（origin・fixStatus・eolDate）を 2.4 にも行う。
- `sources` の検査（`db.sources` が空でない配列であることは今のまま）:
  - schema 2.4: 全要素が次を満たさなければ throw。プレーンなオブジェクト／`name` が空でない文字列（120 文字以下、UNSAFE_TEXT なし）／`url` が `https://` で始まる文字列／`license` のキーがあり、値は `null` か空でない文字列／`licenseNote` は無いか空でない文字列（300 文字以下、UNSAFE_TEXT なし）／`license` か `licenseNote` の少なくとも一方が空でない／`retrievedAt` は `null` か `Date.parse` できる文字列／`recordCount` は 0 以上の整数／`ecosystem` は無いか `null` か文字列。文字列の要素は throw。
  - schema 2.3 以前: 文字列の要素（空でない）は従来どおり受け付ける。オブジェクトの要素も、上の検査を満たせば受け付ける（既存テストに、2.4 の出力の schemaVersion だけを '2.2' に替えて通すものがあるため）。

### 4. `scripts/advisories/lib/psl.mjs`（`renderPslGeneratedTs`）

- 先頭の `/** ... */` コメントの中（最初の `export` より前）に、次の趣旨の行を足す。生成日時などの変わる値は入れない（決定的な出力）。snapshot・fallback のどちらでも出してよい（fallback の一覧も PSL の部分集合なので、出しておく方が安全側）。

```
 * このファイルのルールは Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat) から生成しています。
 * This Source Code Form is subject to the terms of the Mozilla Public
 * License, v. 2.0. If a copy of the MPL was not distributed with this
 * file, You can obtain one at https://mozilla.org/MPL/2.0/.
```

- export する定数（`PSL_SOURCE`・`PUBLIC_SUFFIX_LIST`・`PUBLIC_SUFFIX_WILDCARDS`・`PUBLIC_SUFFIX_EXCEPTIONS`）の名前・型・中身は変えない。
- `src/security/psl-rules.generated.ts` は、夜のシェルの `npm run spec:generate`（`writeGeneratedPslModule`）で作り直される。実装の担当が先に生成しておいてもよい（`node scripts/advisories/lib/psl.mjs`。ネットワークは使わない）。手で書き換えない。

### 5. `scripts/ci/check-data-sources.mjs`（新規）と `.github/workflows/ci.yml`

```js
/**
 * @param {{ db: object, noticesText: string | null | undefined }} input
 * @returns {{ ok: boolean, issues: string[], warnings: string[] }}
 */
export function checkDataSources({ db, noticesText }) { ... }
```

- issues（1 つでもあれば `ok: false`）: `db.sources` が空でない配列でない／文字列の要素がある／`license` も `licenseNote` も無い要素がある／`db.distro._source` に `license` も `licenseNote` も無い要素がある／`noticesText` が文字列のとき、`name` も `url` も本文に含まれない出典がある（issue の文に、その出典の `name` を入れる）。
- warnings: `noticesText` が `null` か `undefined` なら「THIRD_PARTY_NOTICES.md が無いため、出典の照合を飛ばしました」の趣旨を 1 件入れる（`ok` には影響しない）。
- CLI: `node scripts/ci/check-data-sources.mjs [--db <path>] [--notices <path>]`。既定はリポジトリの `src/detection/advisory-db.json` と `THIRD_PARTY_NOTICES.md`（リポジトリの位置は `import.meta.url` から求める）。`--notices` のファイルが無ければ `noticesText: null`。合格なら終了コード 0、不合格なら 1。warnings と issues は標準出力か標準エラーに出す（「THIRD_PARTY_NOTICES」か「NOTICES」の語を含める）。
- 入口の判定は build-db.mjs の `isMainModule()` と同じく `fs.realpathSync(process.argv[1])` で比べる。
- ci.yml: `Check content-script is an IIFE` の後に、手順を 1 つ足すだけ。

```yaml
      - name: Check bundled data sources and licenses
        run: node scripts/ci/check-data-sources.mjs
```

### 6. 拡張機能の側（`src/shared/types.ts`、`src/detection/advisory.ts`）

```ts
// src/shared/types.ts
/** advisory-db.json の sources の要素（v1.8.2 T06。schema 2.3 以前の文字列は名前だけの要素にそろえる） */
export interface AdvisoryDbSourceRecord {
  name: string;
  url: string | null;          // https のみ。古い文字列・不正な値は null
  ecosystem: string | null;
  license: string | null;
  licenseNote?: string;        // 空でない文字列のときだけ
  retrievedAt: string | null;  // Date.parse できる文字列のときだけ
  recordCount: number | null;  // 0 以上の整数のときだけ。古い文字列は null（0 にしない）
}
// AdvisoryDbMetadata に任意の項目を足す（sources: string[] は変えない）
  sourceRecords?: AdvisoryDbSourceRecord[];
```

```ts
// src/detection/advisory.ts
export function normalizeAdvisoryDbSources(raw: unknown): AdvisoryDbSourceRecord[];
```

- 配列でなければ `[]`。要素が空でない文字列（前後の空白を除いて）なら `{ name, url: null, ecosystem: null, license: null, retrievedAt: null, recordCount: null }`（licenseNote は付けない）。要素がオブジェクトで `name` が空でない文字列なら、上の型の注記どおりに各項目を検証して写す（型の違う値は `null`、`licenseNote` は付けない）。それ以外の要素は捨てる。例外を投げない。順番は保つ。
- `AdvisoryDatabase.sources` の型を `Array<string | AdvisoryDbSourceRecord>`（任意）にする。
- `getAdvisoryDbMetadata()`: `sourceRecords = normalizeAdvisoryDbSources(advisoryDb.sources)`、`sources = sourceRecords.map((s) => s.name)`。`advisoryDb.sources` が無いときの既定の文字列の一覧（今の 4 件）は従来どおり `sources` に使い、`sourceRecords` もその正規化にする。
- 照合（`matchOfflineAdvisories` など）は `sources` を読まないので変えない。
