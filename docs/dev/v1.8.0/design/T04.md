# T04 設計メモ — WAF・ボット確認画面の検出と表示

## 目的

取得したページが WAF・ボット対策の確認画面（Fastly の Client Challenge など）だったときに、レポートに `interstitial: { vendor, evidence[] }` を持たせ、ポップアップと Markdown の先頭に「確認画面を診断している可能性」を出す（G6）。調査の完全性を partial にする。診断は止めない。

## 仕様の解釈

| # | 受け入れ条件・指示 | テストで確かめる形 |
| --- | --- | --- |
| A1 | Fastly の確認画面のスナップショット（`tests/fixtures/snapshots/www.drupal.org.*`）で Fastly と判定される | スナップショットの HTML を文書に入れ、`extractDomSignals` → `executeInspection`（ヘッダーはスナップショットのもの）で `report.interstitial.vendor === 'Fastly'`、`evidence` が 2 件以上で、どれも Fastly の印（`Client Challenge` / `fastlyLogo` / `captchaTitle`）を示す。ヘッダー未観測でも同じ結果 |
| A2 | それ以外の全スナップショットとフィクスチャで誤判定 0 件 | スナップショットのディレクトリの残り全件、`tests/fixtures/dom-signal-fixtures.ts` の全件、`tests/fixtures/reports/*.json` の全件で `interstitial` が無く（`undefined` または `null`）、Markdown に注意の文言が出ない |
| A3 | reports:lint が通る | 確認画面のレポート（Fastly・Cloudflare・AWS WAF）と生成した Markdown の組が `lintReportPair` で `ok`。既存のフィクスチャのディレクトリが `lintDirectory` で `ok` |
| B1 | 判定は「同じベンダーの印が 2 つ以上」か「ベンダーのヘッダー 1 つ」 | 陽性: タイトル + `fastlyLogo`、`fastlyLogo` + `captchaTitle`、`cf-mitigated: challenge` だけ、`x-amzn-waf-action: captcha` / `challenge` だけ。陰性: タイトルだけ、`fastlyLogo` だけ、`captchaTitle` だけ、`/cdn-cgi/challenge-platform/` だけ、別のベンダーの印を 1 つずつ（Fastly のタイトル + Cloudflare のパス） |
| B2 | ヘッダーを使うものは取得するヘッダー（G5）に足す | `ALLOWED_RESPONSE_HEADERS` に `cf-mitigated` と `x-amzn-waf-action` がある。`filterAndSanitizeHeaders` が 2 つを残し、`set-cookie` は捨てる |
| B3 | ポップアップと Markdown の先頭に注意を出す。完全性を「不完全」にする | Markdown: `## 1. 調査概要` より前に、G6 の文言「確認画面を診断している可能性」、ベンダー名、「不完全」が出る。ポップアップ: `renderInterstitialNoticeHtml(info)` が同じ 3 つを含む HTML を返し、無いときは空文字。`popup.ts` がこの関数を呼ぶ。`coverage.overallStatus === 'partial'` で、`partialReasons` に「確認画面」を含む理由がある |
| B4 | 診断は止めない（G6） | 確認画面でも `securityChecks` が空でない |

解釈と理由:

- **「不完全」**: 既存の完全性の値は `complete` / `partial` / `unavailable` だけ。新しい値を足すと履歴・ダッシュボード・チェッカーに影響が広がるので、`overallStatus` は既存の `partial` にし、理由（`partialReasons`）に確認画面のことを書く。言葉としての「不完全」は注意の文に入れる（Markdown とポップアップ）。完全性の表示ラベル（「一部制限あり (Partial)」）は変えない。
- **印はベンダーごとに数える**: 別のベンダーの印を合わせて 2 つにしない（安全側）。
- **ヘッダーの値**: `cf-mitigated` は値が `challenge`（大文字・小文字を区別しない）のときだけ印とする（Cloudflare の文書で唯一の値）。`x-amzn-waf-action` は `captcha` か `challenge` のときだけ印とする（AWS の文書にある値）。それ以外の値はテストでは `cf-mitigated: other` が陰性であることだけを確かめる。
- **ヘッダーの観測**: ヘッダーは `executeInspection` が観測済みと判断したもの（origin が一致したキャッシュ）だけを使う。別の origin のキャッシュにある `cf-mitigated` では判定しない。
- **`/cdn-cgi/challenge-platform/`**: Cloudflare の JavaScript Detections は普通の HTML ページにもこのパスのスクリプトを挿入する（外部の事実）。したがって 1 つの印にしかならず、単独では判定しない。Cloudflare のページ内の印として一次資料で確かめられたものは他に無いので、実際には Cloudflare はヘッダーで判定する。
- **タイトル**: `Client Challenge` は前後の空白を除いた完全一致（大文字・小文字の扱いは実装に任せる。テストは完全一致の場合だけを見る）。
- **evidence の形**: `string[]`。各要素は、どの印かが分かる短い文字列（例: `title: Client Challenge`、`id="fastlyLogo"`、`cf-mitigated: challenge`）。テストは、ヘッダーで判定したときにヘッダー名が含まれること、Fastly のときは印の名前のどれかを含むことだけを見る。文言の一字一句・順番は見ない。
- **他の印**: 指示書の候補以外は採用しない（一次資料で確かめられた、確認画面だけに出る印が見つからなかった）。
- **ベンダー名**: `'Cloudflare'` / `'AWS WAF'` / `'Fastly'` の 3 つ。複数のベンダーの条件が同時に成り立つ場合はテストしない（ヘッダーで判定したものを優先するのを推奨）。
- **フィクスチャ**: 「フィクスチャ」は `tests/fixtures/` 以下の DOM シグナルのフィクスチャとレポートのフィクスチャとする。test-server のページは対象にしない（設計の工程では起動しない）。

## 実装の方針

1. **型**（`src/shared/types.ts`）
   ```ts
   export type InterstitialVendor = 'Cloudflare' | 'AWS WAF' | 'Fastly';
   export interface InterstitialInfo {
     vendor: InterstitialVendor;
     /** 判定に使った印（例: 'title: Client Challenge', 'id="fastlyLogo"', 'cf-mitigated: challenge'） */
     evidence: string[];
   }
   // InspectionReport に任意で追加（過去の履歴を壊さない）
   interstitial?: InterstitialInfo;
   ```
   `DomSignals` に、Content Script が集めた確認画面の印を入れる任意のフィールドを足す（名前は任意。例: `interstitialMarkers?: string[]`。`fastlyLogo` / `captchaTitle` の id があるかを `document.getElementById` で見る）。タイトルは既存の `title`、`/cdn-cgi/challenge-platform/` は既存の `scriptUrls` / `resourceEntries` の URL のパスで見てよい。
2. **判定**（新規 `src/detection/interstitial.ts` を推奨）
   `detectInterstitial(dom: DomSignals, responseHeaders: Record<string, string[]>): InterstitialInfo | undefined`
   - ヘッダー: `cf-mitigated` の値が `challenge` → Cloudflare。`x-amzn-waf-action` の値が `captcha` / `challenge` → AWS WAF。どちらも 1 つで判定する
   - ページ内の印: ベンダーごとに数え、2 つ以上で判定する。Fastly: タイトル `Client Challenge`、id `fastlyLogo`、id `captchaTitle`。Cloudflare: `/cdn-cgi/challenge-platform/` で始まるパスのスクリプト・読み込み済みリソース（1 つ）
   - ページ由来の値（タイトル）は信頼しない。evidence には固定の印の名前を入れ、ページの文字列をそのまま長く入れない
3. **統括**（`src/background/service-worker.ts` の `executeInspection`）
   - 観測済みのヘッダー（`responseHeaders`）と `domSignals` で `detectInterstitial` を呼び、`rawReport.interstitial` に入れる（無ければフィールドを入れない）
   - 検出したら、`coverage.overallStatus` を `partial` にし、`coverage.details.partialReasons` に「確認画面」を含む理由を足す（例: `WAF・ボット対策の確認画面（Fastly）を診断している可能性があります`）。`assessInspectionCoverage` に任意の入力（例: `interstitialVendor?: string`）を足す形でも、後から書き足す形でもよい
   - 診断（技術検出・セキュリティ診断）は止めない
4. **取得するヘッダー（G5）**: `ALLOWED_RESPONSE_HEADERS` に `cf-mitigated` と `x-amzn-waf-action` を足す（例: 判定モジュールから `INTERSTITIAL_HEADER_NAMES` を export して組み込む）。G5 の他のヘッダーは T06 の範囲なので、このタスクで足す必要はない
5. **Markdown**（`src/export/markdown.ts` の `generateMarkdownReport`）: `report.interstitial` があるとき、タイトル部の後・`## 1. 調査概要` の前に注意（例: `> [!WARNING]` のブロック）を出す。文には「確認画面を診断している可能性」、ベンダー名、「技術検出の結果は不完全」の旨を入れる。evidence は `escapeMarkdownTableCell` などで無害化する。無いときは何も出さない
6. **ポップアップ**（`src/popup/render.ts`）: `export function renderInterstitialNoticeHtml(info: InterstitialInfo | null | undefined): string` を追加する。無いときは `''`。あるときは Markdown と同じ内容の注意の HTML（値はすべて `escapeHtml()`、インラインイベントハンドラなし）。`src/popup/popup.ts` の `renderReport` / `renderTechnologies` で、一覧の先頭にこの HTML を入れる
7. 文書（仕様書・PRIVACY_POLICY）の更新は任意。PRIVACY_POLICY の G5 の記述は T09 で人が承認する

テストが前提にしている公開 API: `executeInspection`、`ALLOWED_RESPONSE_HEADERS`、`filterAndSanitizeHeaders`（`src/background/service-worker.ts`）、`extractDomSignals`（`src/content/content-script.ts`）、`generateMarkdownReport`（`src/export/markdown.ts`）、`renderInterstitialNoticeHtml`（`src/popup/render.ts`、新規）、`InspectionReport.interstitial`（新規）、`lintReportPair` / `lintDirectory`（`scripts/report-lint.mjs`）。

## 実装の担当への注意

- `tests/` と設計メモは変更しない。
- 既存テスト `tests/content-script.test.ts` は、同じスナップショット（Fastly）で通信先と R04・R08 を確かめている。T04 の後はこのレポートの完全性が partial になるが、R08（完全なときに通信先がある）には影響しない。Drupal が検出されないことも変えない（確認画面から Drupal を推定しない）。
- 完全性を partial にするのは確認画面を検出したときだけ。普通のページの完全性（既存の coverage のテスト）を変えない。
- `cf-mitigated` / `x-amzn-waf-action` はセキュリティ診断ではないので、`HEADER_DEPENDENT_CHECK_PREFIXES` に足すものは無い。新しいセキュリティチェック ID も作らない（作る場合は重大度 LOW 以下、G4）。
- ヘッダーは `executeInspection` が観測済みと判断したもの（origin が一致したキャッシュ）だけを使う。
- ページ由来の値（タイトルなど）は信頼しない。HTML に入れるときは `escapeHtml()`、Markdown では既存の無害化関数を通す。インラインイベントハンドラを使わない。
- `/cdn-cgi/challenge-platform/` は普通のページにも出る。単独で判定しないこと。
- `scripts/report-lint.mjs` は変えなくても通る見込み。変える場合は、既存の `tests/report-lint.test.ts` の期待値を壊さないこと。
- 実サイトのホスト名をコード・文書に書かない（スナップショットのファイル名を参照するのはテストだけ）。
