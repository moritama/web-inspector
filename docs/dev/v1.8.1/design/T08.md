指示書が曖昧な点と、どう解釈したか（安全側：断定しない・警告を増やしすぎない）。

1. **版の一致のテストを足さない。** C12 の項目は、v1.7.1 T12・v1.8.0 T09 のテストがすでに package.json の版を期待値にして確かめている。版を上げる前（package.json が 1.8.0）でも通るので、新しいテストは「目標の版になったか」を見られない（見るには版を直書きする必要があり、K3 に反する）。目標の版は C12 とスクリプトの検査（package.json を一時的に 1.8.1 にして test-hygiene を走らせる）に任せる。manifest は C12 が完全一致を見るので、**4 つ目の番号を付けずに** 1.8.1 にする。
2. **PRIVACY_POLICY の文面。** 文面は人が承認するので、テストは要点（同梱・Debian / Ubuntu の修正情報・送信しない・収集する情報が増えない）だけを見る。版の見出し（`v1.8.1 and later`）はテストしない（次の版でテストが壊れないように）。要点は、**英語と日本語それぞれ 1 行の箇条書き**にまとめる前提で、同じ行の中を検査する。下の「実装の方針」に文案を書いた。
3. **「収集する情報は増えない」の確かめ方。** 文面に加え、manifest の権限がすべてプライバシーポリシーの表に書かれていることを確かめる（権限を足せばテストが落ちる）。取得するヘッダーの許可リストの件数は版や件数の直書きになるので見ない（権限が起点と同じことは総合チェック R04 が見る）。
4. **README に書くこと。** 指示書は「README（カバレッジ表は spec:generate）」とだけ書いている。版の見出しとバッジは A1 の既存テストで見る。今回の機能（NEW-04）を機能一覧に 1 行足すことは「文書」の範囲と解釈し、テストは「NEW-04 の行があり Debian / Ubuntu に触れている」「その行で推定の結果を断定しない（H4）」だけにした。
5. **帰属表示（H2）。** 画面と同梱文書での帰属表示（Ubuntu のデータは CC-BY-SA 4.0）は v1.8.2 で行う（H2）。PRIVACY_POLICY と README にはライセンスの文言を入れない（テストもしない）。
6. **`minExtensionVersion` と `MIN_EXTENSION_VERSION`。** 指示書は変えるとしていない。保守ガイド §1.2 の「スキーマ互換性が変わらない更新では `1.7.0` のまま」に従い、変えない（DB は拡張に同梱され、distro 節の無い DB でも第1段階で動く。§5.3）。

### 2. PRIVACY_POLICY.md

第 1 章「No Data Transmission (外部送信ゼロ)」の英語の箇条書きの最後と、日本語の段落の後に、それぞれ **1 行の箇条書き**で v1.8.1 の項を足す。冒頭の `Last updated` は実装した日に直してよい。文案（人が承認する。要点を変えなければ言い回しは変えてよい）:

- 英語:
  `- **v1.8.1 and later**: The bundled offline database now also includes OS distribution security fix data (Debian / Ubuntu package versions in which each CVE was fixed, from OSV) and OS release support periods (from endoflife.date). This data is bundled with the Extension and used only for local matching; the Extension does not send the Server header, detected versions, or any other data to OSV, Debian, Ubuntu, or any other service. The information the Extension collects does not increase: no new response headers, permissions, or page data are collected.`
- 日本語:
  `- **v1.8.1以降**: 同梱のオフラインデータベースに、OS ディストリビューションの修正情報（OSV の Debian / Ubuntu データにもとづく、CVE ごとの修正済みパッケージ版）と OS リリースのサポート期間（endoflife.date）を加えました。これらは拡張機能に同梱され、端末内での照合にだけ使います。Server ヘッダーや検出したバージョンなどを OSV・Debian・Ubuntu その他の外部サービスへ送信することはありません。収集する情報は増えていません（取得するレスポンスヘッダー・権限・ページの情報の追加はありません）。`

注意: 英語の行に日本語（かな）を入れない。日本語の行にはかなが必ず入る。どちらの行にも `Debian` と `Ubuntu` を書く。第 1 章の既存の文（`no external network connections`、`外部の解析サーバー等への通信も一切行いません`）と第 4 章の権限の表は変えない。

### 3. docs/MAINTENANCE_GUIDE.md

第 2 章（脆弱性データベースの更新手順）の末尾、`### 2.8` の後に、新しい節 `### 2.9 OS ディストリの対応表（distro-map.json）の更新手順 (v1.8.1 / NEW-04)` を足す。この 1 つの節（`####` の小見出しは使ってよい）に次をすべて書く:

- 対応表のファイル `data/advisories/distro-map.json` は人が編集する curated で、各項目に `evidenceUrl`（確かめた一次資料）と `verifiedAt`（確かめた日）を必ず書くこと
- 週次の突き合わせ `scripts/advisories/check-distro-map.mjs`（advisory-db-update.yml のステップ）が、Launchpad の API（Ubuntu）と sources.debian.org の API（Debian）で公開中の版を取り、対応表に無い上流版を「ずれ」として `build-report.json` の `distroMapDrift` と、週次のボット PR の本文の「対応表のずれ」に載せること。API が失敗したら「未確認」になること
- 突き合わせは対応表を**自動では書き換えません**。ずれの報告を受けたら、**人が一次資料**（Launchpad のソースパッケージの公開履歴、Debian の tracker・changelog など）で確かめてから対応表を更新し、`evidenceUrl` と `verifiedAt` を直すこと
- 更新した後は build-db で DB を作り直し（`npm run advisories:build`）、`npm run advisories:validate` と `npm test` で確かめること（§2.3 の手順に合わせる）

### 4. README.md

- 「機能一覧」の表（`## 機能一覧 (v…)` の下）に `NEW-04` の行を 1 行足す。例:
