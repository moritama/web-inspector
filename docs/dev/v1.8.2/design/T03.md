# T03 設計メモ: Cookie のスコープと確信度（A）＋Cookie の保存先（D-3）

## 目的

親ドメイン（`.example.com` など）の Cookie 名だけで技術を high と検出する誤検知を直す（A、H1〜H3、指示書 §4.1）。あわせて、シークレットのタブを調べるときに通常の保存先の Cookie を読んでしまう不具合を、調べるタブの保存先の `storeId` を渡して直す（D-3、H13、指示書 §4.5）。

## 仕様の解釈

受け入れ条件（指示書 §6 T03）と §4.1・§4.5 を、テストで確かめられる形に言い直す。

### A: Cookie のスコープと確信度

1. **スコープの決め方**（§4.1 の表、H1・H3）。Cookie 名ごとにスコープを 1 つ決める。
   - `input.network.cookies`（chrome.cookies）: `hostOnly === false` → `domain`。`hostOnly === true` → `host`。
   - `Set-Cookie` レスポンスヘッダー（ヘッダー名の大文字小文字は問わない）: `Domain` 属性（属性名の大文字小文字は問わない）があり、値が空でなければ `domain`（値がホストと同じでも。RFC 6265 §5.3 の 6）。`Domain` 属性が無ければ `host`。
   - `input.dom.cookiesFromDocument`: 他の経路に無い名前だけ `unknown`。
   - 同じ名前が複数あるとき（経路をまたぐ場合も、同じ経路で 2 件の場合も）: 1 つでも `host` があれば `host`。`host` が無く `domain` が 1 つでもあれば `domain`。どちらも無ければ `unknown`。並び順に依らない。
   - H1 のとおり、Public Suffix List やドメインの文字列とホスト名の比較は使わない。apex のホスト（`example.test` で `.example.test` の Cookie、`hostOnly: false`）も `domain`。
2. **確信度を下げる条件**（H2）: 技術の根拠（重複を除いた後）が**すべて** `cookie-name` で、**どれも** `host` でない（`domain` か `unknown`）。このとき確信度 35、level `low`、`runtimeStatus` は `possible`、`detectionMethod` は `'direct'` のまま。根拠に `cookie-name` 以外（script-url・header など）が 1 つでもあれば下げない。1 つの技術に別々の Cookie 名が複数あるとき、1 つでも `host` なら下げない。
3. **根拠のスコープ**（§4.1「cookie-name の根拠にスコープを持たせる」）: 属性を足す方にした。`cookie-name` の根拠に `cookieScope`（`'host' | 'domain' | 'unknown'`、上の 1 で決めた名前ごとの値）を付ける。detail の文言は T03 では変えない（注記は T04）。
4. **下げた技術を一覧に残す**: 今の採用しきい値（確信度 50 未満を捨てる。`engine.ts` 1052 行）のままだと、35 に下げた技術は一覧から消え、受け入れ条件の「GA は low・possible」を確かめられない（T04 の目視も「GA が low」）。そこで、**従来なら一覧に出ていた（下げる前の確信度が 50 以上だった）**技術に印 `cookieScopeDowngraded: true` を付け、しきい値の対象から外す。
   - 下げる前から 50 未満だったもの（親ドメインの `csrftoken` だけの Django など）は、従来どおり一覧に出さない（警告を増やしすぎない。安全側）。
   - `consolidateCandidates` の「汎用の `*_session` と `XSRF-TOKEN` が揃えば確信度 70」は、2 の条件を満たす（どちらの Cookie も host でない）ときは引き上げない。H2「根拠がすべて Cookie 名で、どれも host-only でない → 35」に合わせるため。結果として従来どおり一覧から外れてよい（テストは「出ないか、出ても low・35 以下」を確かめる）。
5. **連動検知**（受け入れ「下げた技術から連動する技術が high にならない」）: 連動のきっかけは確信度 50 以上の技術だけ（`resolveImplications`）なので、35 に下げた技術は連動のきっかけにしない（`cookieScopeDowngraded` を理由にきっかけに加えない）。親ドメインの `laravel_session` だけのとき、PHP は high にならない（出ないか low）。対照として host-only の `laravel_session` では従来どおり PHP が連動する。
6. **ASP の排他判定**（受け入れ「ASP の排他判定は従来どおり」）: `cookieNameList`（Classic ASP / ASP.NET の排他判定）は名前のスコープを見ず、Map のキー（すべての経路の名前）から作る。親ドメインやスコープ不明の `ASPSESSIONID*` でも、ASP.NET の除外と Classic ASP の signal の抑止は従来どおり働く。そのうえで、残った技術に 2 の規則が当たる（親ドメインの `ASPSESSIONID*` だけなら Classic ASP は low）。

**曖昧だった点と判断**

- **`hostOnly` が無い Cookie（chrome.cookies の経路）**: §4.1 の表は `true`／`false` だけを定める。Chrome の `cookies.Cookie.hostOnly` は必須の真偽値なので、実際の調査では起きない。既存テストと合成データの多くが `hostOnly` を書かずに Cookie を渡している（`tests/detection.test.ts` の `laravel_session`・`XSRF-TOKEN`・`ARRAffinity`・`AWSALB` など 20 件以上、`tests/service-worker.test.ts` の既定の deps）。これらを壊さないよう、`hostOnly` が真偽値でないときは**従来どおり `host`（下げない）**とした。H1 に従い、`domain` の先頭の `.` などの文字列からは推測しない。テスト「互換: hostOnly の無い Cookie」でこの解釈を固定する。
- **`Set-Cookie` の `Domain=`（値が空）**: RFC 6265 §5.2.3 は空の Domain 属性を無視するとしているので `host` 扱い。受け入れ条件の外なのでテストには入れない。
- **`Set-Cookie` は実際の調査ではほぼ届かない**: ヘッダーの記録（`sanitizeHeaders`）が `set-cookie` を落とすため。§4.1 の表と受け入れ条件にあるので、検出エンジンの入力としてテストする。
- **確信度の値**: 下げる前の確信度が 35 未満（例: 単独の `XSRF-TOKEN`）でも、条件を満たせば `Math.min(元の値, 35)` でよい（35 より上げない）。どのみち一覧に出ない。
- **D-3 の「見つからないとき」**: タブ ID がどの保存先の `tabIds` にも無い、`getAllCookieStores` が無い、例外・reject になる、タブ ID が渡されない、のすべてを「見つからない」として扱い、`storeId` を**キーごと**付けない（`storeId: undefined` も付けない）。調査は止めない。
- **保存先 "0" が見つかったとき**: タブ ID を含むのが通常の保存先 "0" なら `storeId: '0'` を渡す（指定なしと同じ結果。§4.5 は見つかった保存先を渡すとだけ書いている）。

### D-3: Cookie の保存先

7. `resolveCookieStoreId(tabId, cookiesApi)` は、`cookiesApi.getAllCookieStores()` の結果から、`tabIds` に `tabId` を含む保存先の `id` を返す。保存先が 3 つ以上あっても、先頭ではなくタブを含むものを選ぶ。見つからなければ `undefined`。
8. `getInspectedCookies(url, tabId)` は、7 で得た `storeId` を、通常の `getAll({ url, storeId })` と分割 Cookie の `getAll({ url, partitionKey: { topLevelSite }, storeId })` の**両方**に渡す。シークレットのタブ（保存先 "1"）では保存先 "1" の Cookie だけが入り、保存先 "0" にしか無い Cookie は入らない。
9. 見つからないときは、従来どおり `getAll({ url })` と `getAll({ url, partitionKey })`（`storeId` のキーなし）。
10. `executeInspection` は `deps.getInspectedCookies(url, tab.id)` と、調べるタブの ID を渡す。
11. manifest の `incognito` は変えない（キーが無い＝既定の spanning のまま。H13）。ヘッダー未観測の文言は T08。

## 実装の方針

変更してよい場所: `src/shared/types.ts`、`src/detection/engine.ts`、`src/background/service-worker.ts`、`docs/`（設計メモを除く。任意）。`tests/` と設計メモは変更しない。ルール JSON と manifest は変えない。

### 1. `src/shared/types.ts`

```ts
/** Cookie のスコープ（v1.8.2 T03 / H1・H3）。host = host-only、domain = Domain 属性あり（親ドメイン・apex を含む）、unknown = document.cookie にだけある */
export type CookieScope = 'host' | 'domain' | 'unknown';
```

- `Evidence` に任意で `cookieScope?: CookieScope;` を足す（`cookie-name` の根拠だけに付ける）。
- `DetectedTechnology` に任意で `cookieScopeDowngraded?: boolean;` を足す（根拠が host でない Cookie 名だけのため確信度を 35 に下げ、従来なら一覧に出ていた技術に `true`。下げていない技術にはキーを付けない。T04 が注記に使う）。

### 2. `src/detection/engine.ts`

- 259〜288 行の `uniqueCookieNames`（`Set<string>`）を `Map<string, CookieScope>` に置き換える（名前は任意。以下 `cookieScopes`）。足すときの合成は `host` > `domain` > `unknown`（強い方を残す）。
  - chrome.cookies: `c.hostOnly === false` → `domain`、それ以外（`true` または真偽値でない）→ `host`。
  - Set-Cookie: 名前は最初の `=` より前を trim（今の処理のまま）。属性は最初の `;` より後を `;` で分け、各項目の `=` より前を trim して小文字で `domain` と比べ、`=` より後を trim して空でなければ `domain`。それ以外は `host`。
  - document.cookie: `unknown`（合成の規則で、他の経路の値が残る）。
- `cookieNameList = Array.from(cookieScopes.keys())`。排他判定（`hasAspSessionIdCookie` など）はそのまま。
- `case 'cookie'` のループは `cookieScopes` のキーを回し、`addEvidence` の根拠に `cookieScope: cookieScopes.get(name)` を足す。それ以外の項目（type・name・value・source・detail・weight）は変えない。
- 確信度（936 行の `calculateConfidence` と Bootstrap の補正の直後）:
  ```ts
  const cookieOnlyNonHost =
    cleanedEvidences.length > 0 &&
    cleanedEvidences.every((e) => e.type === 'cookie-name' && e.cookieScope !== 'host');
  let cookieScopeDowngraded = false;
  if (cookieOnlyNonHost) {
    cookieScopeDowngraded = confidence >= 50; // 従来なら一覧に出ていた
    confidence = Math.min(confidence, 35);
    level = 'low';
  }
  ```
  `results.push` で `...(cookieScopeDowngraded ? { cookieScopeDowngraded: true } : {})`。`detectionMethod: 'direct'` と `runtimeStatus: level === 'high' ? 'confirmed' : 'possible'` は今のまま（自動で `possible`）。
- `consolidateCandidates` の「`*_session` と `XSRF-TOKEN` の両方で確信度 70」の分岐: Laravel の根拠がすべて `cookie-name` で、どれも `cookieScope` が `host` でないときは 70 に上げない（今の確信度のまま）。
- 採用しきい値（1052 行）: `r.confidence >= 50 || r.technology.includes('(候補)') || r.cookieScopeDowngraded === true`。
- `resolveImplications` のきっかけ（`r.confidence >= 50`）は変えない。下げた技術をきっかけにしない。
- 連動で既存の技術に根拠を足す処理（1360 行付近）は変えない（連動の根拠が足されれば「他の根拠」があるので、引き上げられてよい）。

### 3. `src/background/service-worker.ts`

```ts
/** getAllCookieStores だけを持つ、差し替え可能な Cookie API（v1.8.2 T03 / H13） */
export interface CookieStoreLookup {
  getAllCookieStores?: () => Promise<Array<{ id: string; tabIds: number[] }>>;
}

/**
 * 調べるタブが属する Cookie の保存先の ID を返す。見つからない・API が無い・例外のときは undefined
 * cookiesApi を省略すると chrome.cookies（無ければ undefined）
 */
export async function resolveCookieStoreId(
  tabId: number | undefined,
  cookiesApi?: CookieStoreLookup
): Promise<string | undefined>;

export async function getInspectedCookies(url: string, tabId?: number): Promise<InspectedCookieInfo[]>;
```

- `resolveCookieStoreId`: 第 2 引数を**省略したとき**（`arguments.length < 2` 相当。既定の引数で書いてよい）は `typeof chrome !== 'undefined' ? chrome.cookies : undefined` を使う。`tabId` が数値でない、`getAllCookieStores` が関数でない、例外・reject → `undefined`。結果の各要素は `typeof id === 'string'` かつ `Array.isArray(tabIds) && tabIds.includes(tabId)` のものを選ぶ。
- `getInspectedCookies`: `const storeId = await resolveCookieStoreId(tabId, chrome.cookies);` → `const storeDetails = storeId ? { storeId } : {};` を、通常の `getAll({ url, ...storeDetails })` と分割 Cookie の `getAll({ url, partitionKey: { topLevelSite }, ...storeDetails })` の両方に渡す。`storeId` が無いときはキーを付けない（既存テスト `tests/service-worker.test.ts` の IMPL-11 が `toHaveBeenNthCalledWith(1, { url })` で見ている）。それ以降（重複の除去など）は変えない。
- `InspectionDependencies.getInspectedCookies` の型を `(url: string, tabId?: number) => Promise<InspectedCookieInfo[]>` にし、`executeInspection` は `deps.getInspectedCookies(url, currentTabId)` と呼ぶ。1238 行の配線（`getInspectedCookies` をそのまま渡す）は変えなくてよい。

### テストが前提にしている公開 API

- `DetectionEngine#detect`（既存）、`Evidence.cookieScope`、`DetectedTechnology.cookieScopeDowngraded`
- `resolveCookieStoreId(tabId, cookiesApi?)`、`getInspectedCookies(url, tabId?)`、`executeInspection`（既存）、`InspectionDependencies`（既存）
- テストは偽の `chrome.cookies` を `globalThis.chrome` に置く。偽の `getAll` は `storeId` が無ければ保存先 "0" を返す

## 期待値を変えた既存テスト

なし。

確かめたこと:

- 既存テストで Cookie を渡すものの多くは `hostOnly` を書いていない。「`hostOnly` が真偽値でない → host」の解釈で、下げられる既存のケースは無い。スナップショット（`tests/fixtures/snapshots/`）の Cookie は `hostOnly` を持ち、親ドメインの `_ga` を持つものは GA の判定を期待値にしていない。
- `cookie-name` の根拠や技術を `toEqual({ ... })`・`toStrictEqual` で全体比較している既存テストは無い（`evidence).toEqual`・`technologies).toEqual` などを検索）。`cookieScopeDowngraded` は下げたときだけキーを付ける。
- `tests/service-worker.test.ts` の IMPL-11 は `getAll` の引数を `{ url }`・`{ url, partitionKey }` の完全一致で見ている。偽の `chrome.cookies` に `getAllCookieStores` が無く、`getInspectedCookies(url)` をタブ ID なしで呼ぶので、`storeId` のキーを付けなければ通る。
- `npx vitest run tests/detection.test.ts tests/service-worker.test.ts tests/test-hygiene.test.ts` は実装の前に通る（135 件）。

## 実装の担当への注意

- **`storeId` が無いときはキーごと付けない**（`{ url, storeId: undefined }` にしない）。既存テストの完全一致と、新しいテストの `'storeId' in details` が落ちる。
- **採用しきい値の例外は `cookieScopeDowngraded === true` だけ**。確信度 35 の技術をすべて残すと、従来は出なかった親ドメインの `csrftoken` などが一覧に増える。
- **連動のきっかけ（`confidence >= 50`）を変えない**。下げた技術を連動のきっかけにすると、PHP などが連動して受け入れ条件に反する。
- **`consolidateCandidates` の 70 への引き上げ**を、host でない Cookie 名だけのときは行わない。下げた直後に別の箇所で上げ直さないこと。
- `Set-Cookie` の値の中の `Domain=`（例: 値そのものに `Domain=` を含む）を属性と取り違えないよう、属性は最初の `;` より後だけを見る。
- `Set-Cookie` の名前の取り方（最初の `=` より前を trim）は今のまま。`hostOnly` の判定に Cookie の `domain` の文字列（先頭の `.` など）やホスト名との比較を使わない（H1）。
- 根拠の detail の文言・ポップアップ・ダッシュボード・Markdown の表示は T03 では変えない（注記と Secure の内訳は T04）。画面に出る文字列は増えない。
- `detectionMethod` を `'inferred'` にしない。新しい区分も作らない（H2）。
- `HEADER_DEPENDENT_CHECK_PREFIXES` は関係しない（新しいセキュリティチェックは足さない）。
- manifest の `incognito` を足さない・変えない（H13）。拡張機能の通信は増えない（chrome.cookies の API だけ）。
- `cookies.ts`（セキュリティ診断の Cookie の分類）は変えない。
